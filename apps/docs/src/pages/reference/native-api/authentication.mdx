# Authentication & authorization

The v0.2 native API authenticates each request, then evaluates current authority for the operation. The generated [native API reference](/reference/native-api) lists the credential requirements for each operation.

## First-party sessions

The dashboard signs in through Better Auth. Better Auth owns `/api/auth/*`. These protocol routes are not native operations.

The native API uses the Better Auth session cookie for browser requests. The local cookie name is `better-auth.session_token`.

The secure cookie name is `__Secure-better-auth.session_token` outside explicit loopback development. Both forms are HttpOnly, SameSite=Lax, and Path=/.

The session API reads persisted session state for every protected request. It does not use a session cache. A missing, expired, or revoked session returns `401`.

The session contract includes these operations:

- read and delete the current session
- list and delete owned sessions
- revoke other sessions
- revoke all sessions

Use the generated reference for the exact method, path, request, response, and Problem Details schema.

## OAuth bearer tokens

The frozen OAuth provider contract supports two access-token journeys:

- delegated person authorization code with mandatory S256 PKCE
- service-principal client credentials

Both journeys issue audience-bound bearer tokens. Only delegated users receive a refresh token. The native resource is `urn:vektorprogrammet:native-api`.

`OAuthUserBearer` resolves to a `Person`. `OAuthServiceBearer` resolves to a `ServicePrincipal`. A service principal is not a synthetic person, membership, role, or `auth.user`.

OAuth scope is not a domain capability, grant, role, membership, ownership fact, or requirement result. Each protected request recalculates authorization against current authority.

## Authorization decisions

Each native endpoint declares one `AccessSpec` beside its contract. The transport resolves the credential and principal. The handler then evaluates the capability, scope, requirements, concealment, and decision time.

A valid credential does not grant access by itself. A denied requirement returns `403` when the operation reveals the resource. A concealed resource can return `404`. An invalid or expired credential returns `401`.

Invitation response operations use an object capability in `X-Recruitment-Invitation-Capability`. The capability identifies one invitation response. The server resolves the capability before it evaluates the pending requirement. Missing, malformed, unknown, or superseded capabilities fail closed.

## HTTP requirements

Every external `POST`, `PATCH`, and `DELETE` requires one `Idempotency-Key` header. The server derives a stable identity from the credential subject, operation ID, target, and key. It does not expose the internal command ID.

Existing-resource mutations also require a validated strong `If-Match` entity tag. The request body does not contain `commandId` or `expectedRevision`.

Native errors use endpoint-specific RFC 9457 Problem Details. The generated reference lists each status and error schema. The historical v0.1 error-tag envelope is not a v0.2 response.

## Source ownership

The access declarations are in `packages/http-api/src`. The identity and authorization services resolve current state in the backend and domain layers. The generated reference remains the canonical operation source.
