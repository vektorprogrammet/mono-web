This amendment narrows and completes the first-party session contract from spec 0054. It is a design contract, not an implementation plan with a partial fallback. The implementation must preserve the 0054 ownership boundary while making session revocation authoritative on the next request.

## 2. Frozen ownership boundary

Better Auth 1.7.1 remains the credential and first-party session engine. It owns email/password verification, session issuance, expiry, cookie serialization, and session revocation inside `AuthLive`. The native domain authorities own roles, memberships, capabilities, scopes, and every authorization decision.

The following invariants remain mandatory:

1. `auth.user.id` is the canonical `PersonId` and must reference `public.person_profiles.person_id`.
2. Better Auth data is identity/session data only. Roles, permissions, departments, grants, and policy are never read from the `auth` schema.
3. Better Auth cookies are first-party browser credentials only. They are not bearer API tokens, OAuth credentials, object capabilities, or service credentials.
4. A normal role cannot mint a browser session for another person. Account or session provisioning is an explicit administrative action and is not a normal user sign-in.
5. Test Layers may inject the typed `Identity` service. Production code must not replace Identity with a token map or a fixture issuer.
6. `session.cookieCache` is absent. Every authoritative API session resolution reads current persisted session state; no cache grace period is allowed after expiry or revocation.

The engine configuration is frozen as the following semantic contract:

```ts
betterAuth({
  emailAndPassword: {
    enabled: true,
    disableSignUp: true,
  },
  session: {
    expiresIn: 60 * 60 * 24 * 7,
    updateAge: 60 * 60 * 24,
    // no cookieCache property
  },
});
```

The exact Better Auth 1.7.1 API shape remains an implementation concern, but `disableSignUp: true`, seven-day expiry, one-day update age, and no authoritative cookie cache are not optional.

## 3. Cookie contract

First-party session cookies MUST have these properties:

| Property   | Contract                                                                                     |
| ---------- | -------------------------------------------------------------------------------------------- |
| `HttpOnly` | Always set; browser script cannot read the session credential                                |
| `SameSite` | `Lax`                                                                                        |
| `Path`     | `/`                                                                                          |
| `Secure`   | Set outside explicit loopback local development                                              |
| Prefix     | Preserve Better Auth's secure-prefix behavior; do not strip or rename a secure cookie prefix |
| Lifetime   | Seven-day session expiry with one-day update age                                             |

The local loopback exception is explicit development composition only. A preview or production origin is not loopback merely because its backend process listens on a local port. Tests must assert the secure cookie and prefix behavior for a non-loopback origin and the non-secure local-development behavior separately.

No response may expose the cookie value, a reusable session token, a raw `Cookie` header, or a credential-bearing `Set-Cookie` value in an evidence artifact or API representation.

## 4. Frozen session resource surface

The external first-party session surface is exactly:

| Purpose                        | Method and path                    | Success behavior                                                                                                                     |
| ------------------------------ | ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| Read current session           | `GET /api/session`                 | Returns the strict current-session projection                                                                                        |
| End current session            | `DELETE /api/session`              | The first authenticated request revokes the current session; later requests with that cookie return `401`                            |
| List current person's sessions | `GET /api/sessions`                | Returns only sessions owned by the authenticated person                                                                              |
| Revoke one session             | `DELETE /api/sessions/{sessionId}` | Revokes one owned session; missing, non-owned, and already-deleted IDs have the same concealed `404`                                 |
| Revoke other sessions          | `POST /api/sessions:revoke-others` | Revokes every owned session except the current session; repeat requests succeed while the current session remains live               |
| Revoke all sessions            | `POST /api/sessions:revoke-all`    | The first authenticated request revokes every owned session, including the current one; later requests with that cookie return `401` |

Session revocation is state-idempotent, not credential-idempotent. The first
authenticated request performs the state transition. Authentication is
resolved before replay, so a request carrying the revoked cookie cannot receive
a second successful response, create another audit transition, or perform
another mutation. `revoke-others` may be repeated because its current session
remains active. A repeated revoke-one after deletion is the same concealed
`404` as a missing or non-owned session.

`/api/me/session` is not a compatibility alias. The implementation must migrate all first-party callers and remove the old external route. Better Auth's `/api/auth/*` handler remains the credential engine surface; it is not the session-management resource surface and must not be copied into the native resource document.

### 4.1 Safe session representation

The session collection and current-session response may expose only these fields:

```text
sessionId   opaque non-token identifier
createdAt   timestamp
updatedAt   timestamp
expiresAt   timestamp
ipAddress   optional sanitized source address
userAgent   optional bounded user-agent value
current     boolean
```

The representation MUST NOT contain a session token, cookie value, refresh token, password, OAuth token, credential, raw header, or any field from which a reusable credential can be reconstructed. `sessionId` is an opaque identifier and is not accepted as a credential.

The list is ownership-only. A person can list and revoke only sessions whose owner is that same canonical `PersonId`. Roles, global administrator status, department membership, and domain permissions do not grant cross-person session access. Missing and non-owned session IDs have the same concealed `404` result.

## 5. State and transition contract

| State       | Entry transition                                             | Allowed observations                                                                       | Exit transition                                      |
| ----------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------ | ---------------------------------------------------- |
| `NoSession` | No cookie, rejected sign-in, rejected sign-up                | `GET /api/session` returns `401` without credential detail                                 | Successful sign-in creates `Active`                  |
| `Active`    | Successful sign-in or persisted session refresh              | Current owner may read/list; current session may be ended; owner may revoke owned sessions | Expiry, current sign-out, one/others/all revocation  |
| `Expired`   | `expiresAt` is reached                                       | Treated as unauthenticated; no authenticated projection                                    | No resurrection; a new sign-in creates a new session |
| `Revoked`   | Current, one, others, or all revocation                      | Next request fails as unauthenticated; it is not a valid list credential                   | No transition back to `Active`                       |
| `Rejected`  | Sign-up attempt, invalid credentials, disallowed origin/CSRF | Safe typed failure and audit event when the event has a subject or request context         | No session is created                                |

Required transition rules:

1. A successful sign-in creates one `Active` session for the authenticated `PersonId` and emits one success audit event.
2. A failed sign-in creates no session and emits one failure audit event without storing the password.
3. `DELETE /api/session` revokes the current session. Only the first authenticated request succeeds; later requests carrying that revoked cookie return `401` and cause no additional mutation or audit transition.
4. `DELETE /api/sessions/{sessionId}` can revoke only an owned session. A missing, non-owned, or already-deleted ID returns the same concealed `404` result.
5. `POST /api/sessions:revoke-others` leaves the current session active and revokes all other owned sessions. Repeating it succeeds because the current session remains active and has no additional semantic effect.
6. `POST /api/sessions:revoke-all` revokes all owned sessions, including the current one. Only the first authenticated request succeeds; later requests carrying that revoked cookie return `401` and cause no additional mutation or audit transition.
7. A revoked or expired session fails on the next request. There is no five-minute cache grace, stale projection, or local-cookie-only success criterion.
8. Every state-changing session action re-evaluates current authentication and ownership. An idempotency key, session ID, role, or path prefix never grants authority.

## 6. CSRF and trusted-origin contract

The implementation retains Better Auth 1.7.1 origin checks. It MUST NOT disable CSRF protection, origin validation, or the framework's action-origin checks to make a browser journey pass.

There is one typed trusted-origin configuration value for the native session boundary. Local, preview, and production composition each provide that value explicitly:

- Loopback local development names the exact dashboard origin used by the local composition.
- Preview composition names the exact preview dashboard origin supplied by the deployment composition.
- Production values remain operator-owned inputs. This spec invents no production hostname, account, route, or secret.

Credentialed requests from an origin outside the configured trusted-origin set are rejected before session mutation or protected-resource dispatch. The rejection is safe, does not disclose credentials, and emits a `trusted-origin/CSRF rejection` audit event when a request correlation is available. A missing origin is not silently upgraded to a trusted cross-origin request. Same-origin browser requests remain valid.

The policy is centralized and applies consistently to Better Auth routes, native session routes, and protected native groups. Wildcard `Access-Control-Allow-Origin: *` is forbidden for credentialed requests.

## 7. Residual token-map removal

Remove all production `AUTH_TOKENS` maps, parsers, environment variables, lookup readers, and callers. This includes admission, receipt, recruitment, organization, and any other production path that authenticates from an opaque environment string.

The only supported production authentication input for a person browser request is the Better Auth first-party session cookie resolved through `Identity`. Test Layers may provide a synthetic `Identity` interpretation, but test fixtures must not be presented as production authentication evidence.

A successful implementation has no production reference to `ADMISSION_AUTH_TOKENS`, `RECEIPT_AUTH_TOKENS`, `RECRUITION_*` token maps, `ORGANIZATION_AUTH_TOKENS`, `jwt_token`, fixture login, or Symfony login routes in the native caller graph.

## 8. Append-only identity security audit

Add a dedicated identity security audit relation. It is not a replacement for domain command audits and it does not store credentials. Each event contains these fields:

| Field                | Contract                                                                                                    |
| -------------------- | ----------------------------------------------------------------------------------------------------------- |
| `eventId`            | Unique opaque event identifier, generated by the owned persistence boundary                                 |
| `occurredAt`         | Authoritative timestamp captured at event creation                                                          |
| `eventKind`          | Closed event-kind identifier from the minimum set below                                                     |
| `subjectPersonId`    | Canonical `PersonId`; nullable only when no subject has been established                                    |
| `sessionId`          | Opaque session identifier; nullable when the event has no session                                           |
| `actorPrincipal`     | Authenticated person or explicit administrative principal; nullable only when no such actor was established |
| `requestCorrelation` | Required for a request-bound event; nullable only when no request exists                                    |
| `sourceIp`           | Optional sanitized source IP                                                                                |
| `userAgent`          | Optional bounded user-agent value                                                                           |
| `details`            | Closed/structured, bounded, non-secret details object                                                       |

Actor principal and subject person are independent fields. A failed sign-in,
rejected sign-up, or trusted-origin/CSRF rejection may have no authenticated
or administrative actor, so `actorPrincipal` is then `null`.
`subjectPersonId` remains separately nullable only when no subject has been
established. A request-bound event MUST carry `requestCorrelation`; it may be
`null` only for an event created without a request context.

The minimum closed event kinds are:

```text
sign-in-success
sign-in-failure
sign-out
session-revoked-one
session-revoked-others
session-revoked-all
sign-up-rejected
trusted-origin-csrf-rejected
account-provisioned-administratively
session-provisioned-administratively
```

The audit MUST NOT store passwords, password hashes, session tokens, cookie values, OAuth tokens, raw cookies, raw headers, arbitrary request bodies, or unbounded provider payloads. Details identify safe outcome codes and bounded metadata only.

The database must enforce append-only behavior. The implementation must establish the owned adapter transaction and ordering boundary for audit writes, including whether an event is committed before or with the Better Auth state transition. Better Auth 1.7.1 does not provide an audit transaction guarantee. Therefore:

1. The implementation must prove its adapter transaction and event ordering with a focused failure/concurrency test.
2. This amendment does not claim audit atomicity merely because a Better Auth operation succeeded.
3. Until that proof exists, evidence MUST state the observed ordering and MUST NOT claim that authentication state and audit state are atomic.
4. Direct update/delete attempts against the audit relation must fail, and the append-only invariant must survive ordinary application credentials.

## 10. Migration and caller impact

Add one migration after the current schema revision using the existing migration runner. The migration must create the identity security audit relation, its closed event-kind constraint, safe indexes, append-only enforcement, and only the foreign keys needed to preserve canonical identity/session references. It must not duplicate Better Auth core tables or copy credential material.

The migration must be applied identically to disposable PostgreSQL and PGlite where the existing test architecture requires both. Migration evidence must show the audit relation is present, writable only through the append path, and absent from the public domain capability inventory as an authorization source.

The implementation must migrate these callers in one cutover:

- `packages/database/src/auth-engine.ts`: disable sign-up and remove `cookieCache`.
- `packages/database/src/auth-live.ts`: preserve the typed `Identity` seam and authoritative session resolution.
- `apps/backend/src/router.ts`: replace `/api/me/session`, add the frozen session resources, and centralize trusted-origin/CSRF handling.
- `apps/backend/src/http-api/transport.ts`: remove pass-through security middleware and wildcard credentialed CORS.
- `apps/dashboard/app/lib/auth.server.ts`: use the new session resource and preserve safe redirect/cookie forwarding semantics.
- Dashboard login/logout and native journey callers: use the new routes and retain the real Better Auth cookie boundary.
- Admission, receipt, recruitment, organization, and related config/caller modules: remove production token-map parsing and lookup.
- Database migrations, test Layers, seeders, and proof runners: record only synthetic, non-secret evidence and never use a fixture token as production authentication.

No compatibility alias, redirect, dual-write path, or deprecated token-map shim is permitted.

## 11. Focused real-browser immediate-revocation journey

The implementation must add or adapt one bounded journey using disposable loopback PostgreSQL, one native backend, one dashboard, and real Chromium. The journey must use synthetic personas only and must retain the old cookie only in memory.

The journey performs these steps:

1. Start the native composition with an explicit local trusted origin and seed two synthetic people through the supported identity seeding path.
2. Sign in one person in two browser contexts. Assert the first-party cookie attributes and that both sessions resolve to the same `PersonId`.
3. Call `GET /api/sessions` and assert only safe metadata fields, opaque session IDs, one `current: true` entry, and no token/cookie/credential field.
4. Revoke the other session with `POST /api/sessions:revoke-others`. Assert the current session remains usable and the other context receives `401` on its next request.
5. Capture the current cookie in memory, call `DELETE /api/session`, and immediately issue concurrent `GET /api/session` requests using that old cookie. Assert every request returns `401`; local cookie deletion alone is not evidence.
6. Repeat `POST /api/sessions:revoke-others` while the current session remains active and assert success. After `DELETE /api/session` or `POST /api/sessions:revoke-all`, any later request carrying the revoked cookie returns `401` and causes no additional mutation or audit transition. Repeat `DELETE /api/sessions/{sessionId}` after deletion and assert the same concealed `404` as a missing or non-owned session.
7. Attempt sign-up and a credentialed request from an untrusted origin. Assert rejection, no session creation or mutation, and the corresponding bounded audit events.
8. Attempt to list or revoke another person's session as a normal role. Assert ownership-only denial and no cross-person metadata disclosure.
9. Inspect the audit relation through a distinct observer connection. Assert the required event kinds, subject/session linkage, bounded non-secret details, append-only enforcement, and the implementation's explicitly observed transaction/ordering result.
10. Assert no browser or backend request reaches Symfony, fixture login, legacy token routes, OAuth routes, or an unexpected origin. Assert no password, token, raw cookie/header, or arbitrary body appears in evidence.

The journey must include a failure or rollback case that demonstrates the audit ordering result. It must not call that result atomic unless the owned adapter proof establishes atomicity.

## 12. Exact falsifiers

The amendment is not implemented if any of these conditions occurs:

- `emailAndPassword.disableSignUp` is absent, false, or bypassed by another public sign-up route.
- `session.cookieCache` remains configured, or an authoritative API request can use a stale cached session after revocation.
- A revoked or expired session succeeds on its next request, or a browser journey proves only local cookie deletion.
- Any external session resource remains at `/api/me/session`, or any frozen route is missing or uses a compatibility alias.
- Session metadata contains a token, cookie, password, OAuth credential, raw header, or reconstructible credential.
- A person lists or revokes another person's session, or a normal role mints another person's browser session.
- A missing and non-owned session are distinguishable, or either leaks ownership information.
- Current or all revocation accepts a later request with the revoked cookie, performs another mutation, or emits another audit transition; revoke-others is not repeatable while the current session remains active; or revoke-one does not repeat the concealed `404` after deletion.
- Better Auth origin checks or CSRF protection are disabled, bypassed, or replaced with an untyped allow-all path.
- A credentialed request from an untrusted origin mutates state or reaches protected dispatch.
- Production uses wildcard credentialed CORS or multiple conflicting trusted-origin sources.
- Secure cookie behavior is absent outside explicit loopback local development, or Better Auth's secure prefix is stripped.
- Any production `*_AUTH_TOKENS` map, parser, reader, fixture login path, `jwt_token`, or Symfony login caller remains.
- The identity security audit permits update/delete, stores a forbidden secret, has an open event-kind union, or omits required identity/request context.
- Audit ordering or transaction behavior is claimed rather than proved, or Better Auth's lack of an audit transaction guarantee is hidden.
- The migration creates a second identity schema, changes domain authorization ownership, or is not applied consistently by the existing runner.
- Evidence uses a stubbed transport, fixture-issued session, production credential, remote database, provider effect, or unbounded request payload.

## 13. Definition of done

1. The amendment is committed as a single design-spec file and remains separate from implementation.
2. Better Auth 1.7.1 is configured with `emailAndPassword.disableSignUp: true`, seven-day expiry, one-day update age, and no authoritative `cookieCache`.
3. First-party cookies satisfy `HttpOnly`, `SameSite=Lax`, `Path=/`, and environment-appropriate `Secure` plus Better Auth secure-prefix behavior.
4. `auth.user.id = PersonId` remains enforced, and roles and policy remain domain-authority concerns.
5. The six frozen session routes exist with strict safe metadata, owner-only list/revoke, concealed `404`, state-idempotent revocation (repeat revoke-others succeeds while current remains active; revoked-cookie retries for current/all return `401` without another mutation or audit transition), and immediate next-request effect.
6. A single typed trusted-origin configuration is composed explicitly for local and preview environments; production values remain operator-owned; untrusted credentialed origins are rejected without disabling CSRF or origin checks.
7. All production authentication token maps and their callers are removed. Test Layers inject only the typed `Identity` interpretation.
8. The identity security audit migration and append-only enforcement exist with the required fields and minimum event kinds. No forbidden credential or raw request material is stored.
9. The owned adapter transaction and event ordering are proved honestly. No audit atomicity claim is made before that proof.
10. Focused model/HTTP/database checks and one real-browser immediate-revocation journey prove the new contracts against disposable state. The browser journey proves persisted revocation, not only cookie deletion.
11. Evidence contains only synthetic personas and sanitized bounded observations, with no provider, production, remote database, credential, token, raw cookie/header, or arbitrary payload effect.

## 14. Explicit deferrals

This amendment does not freeze or implement the following:

- `0055.1` principal, credential, scope, grant, and `AccessSpec` algebra.
- `0082` OAuth, service principals, delegated bearer tokens, refresh-token families, revocation, or introspection.
- `0077.2` the complete operation matrix and route count.
- `0080.1` general Problem Details, cache policy, CORS/idempotency/ETag policy outside the session/origin boundary required here.
- Password migration, password-reset email, 2FA, passkeys, SSO, social providers, impersonation, device flow, personal access tokens, and standalone API keys.
- Provider deployment, production hostname selection, production credentials, remote database state, and release authority.

Those subjects require their own numbered amendment or specification. They must not be smuggled into the session-hardening implementation as compatibility behavior.
