# Design spec 0054.2 — native password recovery

## Metadata

| Field | Value |
| --- | --- |
| Stable ID | `0054.2` |
| Status | Frozen contract. Implementation blocked. |
| Amends | `design-specs/0054-native-identity-better-auth.md` and `design-specs/0054.1-native-identity-session-hardening.md` |
| Source base | `0fbd1f6f66afeafc831d05d70870c2a4a16b3998` |
| Depends on | Better Auth 1.7.1, the 0054.1 identity boundary, and the 0077.2 non-native ingress boundary |
| Blocks on | An operator-approved real `PasswordResetMailDelivery` authority and a password-cohort migration |
| Scope | Password-reset request, mail delivery, callback, credential update, session revocation, audit, and browser evidence |
| Operator boundary | This contract selects no provider, credential, account, hostname, deployment, or release action |

This amendment freezes the native password-recovery contract. It does not authorize implementation or release.

Implementation remains blocked on two prerequisites:

1. An operator must approve a real `PasswordResetMailDelivery` authority.
2. The password-cohort migration must move each released user to the Better Auth credential store.

A recording adapter, a logger, or a no-op callback does not satisfy the first prerequisite. A local proof does not authorize production delivery.

## 1. Current evidence and blocking result

The source base has one Better Auth 1.7.1 engine. Its base path is `/api/auth`.

`packages/database/src/auth-engine.ts` enables email and password authentication. It does not configure `emailAndPassword.sendResetPassword`.

Better Auth 1.7.1 rejects `POST /request-password-reset` when that callback is absent. The error code is `RESET_PASSWORD_DISABLED`.

The source base also has durable outbox patterns. Those patterns do not provide a password-reset mail authority.

The public-application outbox accepts only its three application effect types. The `NotificationGateway` service accepts only recruitment invitation effects.

The Symfony application has a working legacy mail authority. It sends its own reset code and updates its own credential store.

That mail authority does not deliver a Better Auth reset token. It cannot complete the native password-recovery journey.

The dashboard still calls `client.auth.resetPassword` and `client.auth.setPassword`. The v0.2 generated SDK no longer exposes those symbols.

This state is a cutover gap. It is not permission to restore the v0.1 native SDK shape.

### 1.1 Better Auth 1.7.1 authority

The installed Better Auth 1.7.1 package source and types are the API authority for this amendment.

The relevant package paths are:

- `better-auth/dist/api/routes/password.d.mts`
- `better-auth/dist/api/routes/password.mjs`
- `better-auth/dist/context/create-context.mjs`
- `@better-auth/core/src/types/init-options.ts`

The package freezes these facts:

1. The request handler is `POST /request-password-reset`.
2. The callback handler is `GET /reset-password/:token`.
3. The credential update handler is `POST /reset-password`.
4. The default reset-token lifetime is one hour.
5. `revokeSessionsOnPasswordReset` defaults to false.
6. The request handler catches failures from `sendResetPassword`.
7. The reset handler consumes the token before it updates the password.
8. The reset handler updates the password before it deletes sessions.

This amendment makes the lifetime and session deletion explicit. It also closes the callback-failure gap at the owned outer handler.

## 2. Frozen ownership boundary

Better Auth 1.7.1 owns these items:

- reset-token generation and expiry
- the credential-engine verification row
- reset-token validation and consumption
- password policy, hashing, and credential update
- deletion of all sessions after a successful password update

The native identity persistence boundary owns these items:

- durable acceptance of a reset-mail effect
- outbox claim, retry, completion, and quarantine state
- password-recovery security audit events
- safe ordering evidence around the Better Auth handler

`PasswordResetMailDelivery` owns these items:

- provider transport
- provider acknowledgement
- transport timeout behavior
- typed provider failures
- provider idempotency behavior

The dashboard owns the fixed callback page and user-facing state. It does not generate, validate, normalize, or store reset tokens.

The password-recovery client owns request encoding and response decoding. It remains outside the generated native client.

Domain authorities continue to own roles, memberships, capabilities, scopes, and authorization. Password recovery does not grant domain access.

## 3. NativeApi and operation-count boundary

Password recovery is a credential-engine surface under `/api/auth/*`.

It MUST NOT enter `ExternalNativeApi` or `InternalNativeApi`. It receives no native operation ID and no `AccessSpec`.

It MUST NOT enter generated native OpenAPI, generated native SDK operations, or `native-api-operations.json`.

This amendment changes no NativeApi operation count. Design spec 0077.2 and its route-matrix successors own that count.

The existing v0.1 `createClient` factory and `client.auth` namespace MUST NOT return. The complete `client.admin` namespace also remains deleted.

After the blockers close, use one narrow credential client. Its public name is `createPasswordRecoveryClient`.

That client has only these methods:

```ts
interface PasswordRecoveryClient {
  readonly requestPasswordReset: (email: string) => Promise<void>;
  readonly resetPassword: (token: string, newPassword: string) => Promise<void>;
}
```

This client is handwritten because Better Auth is not a NativeApi resource. Its operations do not enter the native operation registry.

## 4. Explicit interim legacy boundary

The released system retains the Symfony credential routes until the two blockers close.

The retained routes are:

```text
POST /api/password_resets
POST /api/password_resets/{code}
```

These routes remain outside both NativeApi roots. They are temporary legacy credential routes, not native aliases.

The dashboard can use one server-only adapter during this interim period. The adapter name MUST identify both Symfony and legacy ownership.

The frozen adapter module name is:

```text
apps/dashboard/app/server/legacy-symfony-password-recovery.server.ts
```

The adapter exports only these operations:

```ts
requestLegacySymfonyPasswordReset(email)
setLegacySymfonyPassword(code, password)
```

The adapter MUST NOT be exported from `@vektorprogrammet/sdk`. It MUST NOT create an `auth` namespace or a general legacy client.

The adapter MUST NOT proxy a Symfony reset into Better Auth. Each credential engine keeps its own reset token and password update.

A user cohort cannot use Symfony reset with Better Auth sign-in. The cohort cutover must move sign-in and reset ownership together.

Keep the dynamic dashboard code route while the legacy adapter owns the journey. Rename that route only during the final native cutover.

Delete the adapter, both legacy callers, and both Symfony routes after the native journey passes. The deletion is one clean cutover.

## 5. Exact native HTTP contract

The configured Better Auth `baseURL` contains the canonical backend origin. Its `basePath` is `/api/auth`.

The configured dashboard origin is `dashboardOrigin`. The only reset page is:

```text
{dashboardOrigin}/tilbakestill-passord
```

### 5.1 Request a password reset

`requestPasswordReset(email)` sends this request:

```http
POST {canonicalOrigin}/api/auth/request-password-reset
Content-Type: application/json
Origin: {dashboardOrigin}
```

The JSON body is exactly:

```json
{
  "email": "user@example.invalid",
  "redirectTo": "{dashboardOrigin}/tilbakestill-passord"
}
```

The public client accepts no callback argument. A caller cannot select another callback path or origin.

A normal response has status `200`. Better Auth returns this semantic shape:

```json
{
  "status": true,
  "message": "If this email exists in our system, check your email for the reset link"
}
```

The client decodes `status: true` and returns `void`. It does not expose the message as proof of delivery.

A malformed email returns Better Auth's bounded `400` response. An untrusted origin or callback returns `403` before credential mutation.

### 5.2 Reset-mail link

The delivery authority uses the URL that Better Auth supplies to `sendResetPassword`.

The URL has this exact shape:

```text
{canonicalOrigin}/api/auth/reset-password/{token}?callbackURL={encodedCallbackURL}
```

`encodedCallbackURL` is the percent-encoded form of:

```text
{dashboardOrigin}/tilbakestill-passord
```

The mail adapter MUST NOT build a direct dashboard token URL. It MUST NOT change, decode, normalize, or append parameters to the supplied URL.

### 5.3 Callback redirect

A browser opens this handler:

```http
GET {canonicalOrigin}/api/auth/reset-password/{token}?callbackURL={encodedCallbackURL}
```

Better Auth validates the token and its expiry. A valid token produces this redirect:

```text
{dashboardOrigin}/tilbakestill-passord?token={token}
```

An invalid or expired token produces this redirect:

```text
{dashboardOrigin}/tilbakestill-passord?error=INVALID_TOKEN
```

The dashboard route is `tilbakestill-passord.tsx`. It is not a dynamic `$code` route.

The route reads `token` or `error` from its own request URL. A missing token uses the invalid-link state.

### 5.4 Set the new password

`resetPassword(token, newPassword)` sends this request:

```http
POST {canonicalOrigin}/api/auth/reset-password
Content-Type: application/json
Origin: {dashboardOrigin}
```

The JSON body is exactly:

```json
{
  "newPassword": "the-new-password",
  "token": "the-reset-token"
}
```

The reset token MUST NOT enter the request query. It MUST NOT enter the dashboard form action path.

A successful response has status `200` and this shape:

```json
{
  "status": true
}
```

An invalid, expired, or consumed token returns `INVALID_TOKEN`. A reused token causes no credential or session mutation.

A password-policy failure returns the Better Auth password-policy error. The dashboard does not replace that authority.

## 6. Password and session contract

The Better Auth configuration MUST include these values:

```ts
emailAndPassword: {
  enabled: true,
  disableSignUp: true,
  minPasswordLength: 12,
  resetPasswordTokenExpiresIn: 60 * 60,
  revokeSessionsOnPasswordReset: true,
  sendResetPassword,
  onPasswordReset,
}
```

The implementation keeps the Better Auth maximum password length. If the implementation sets it explicitly, the value is `128`.

The dashboard uses 12 as its minimum length. It MUST NOT keep the current eight-character rule.

`onPasswordReset` has one narrow purpose. It records the safe `PersonId` in bounded request-local coordination.

`onPasswordReset` performs no mail send, database write, audit write, log write, or session mutation. It never stores the password or token.

A `200` reset response means all of these facts are true:

1. Better Auth consumed the reset token.
2. Better Auth updated the credential password.
3. Better Auth deleted every session for the user.
4. The owned success audit write completed.

The browser can still hold an old cookie. Its next protected request returns `401` because 0054.1 forbids authoritative cookie cache grace.

The old password fails after success. The new password can create one new session.

## 7. Trusted-origin and callback allowlist

The implementation reuses `NATIVE_IDENTITY_TRUSTED_ORIGINS`. It adds no second trusted-origin configuration source.

It also reuses `OAUTH_DASHBOARD_ORIGIN` as `dashboardOrigin`. That exact origin must be a member of the trusted-origin list.

Origin values remain exact origins. They contain no credentials, path, query, fragment, or wildcard.

Local composition retains this one origin:

```text
http://127.0.0.1:5174
```

Preview composition retains one frozen HTTPS preview origin. Production origins remain operator-owned HTTPS inputs.

Better Auth validates the callback origin. The owned outer handler also pins the exact reset-page URL.

For `POST /api/auth/request-password-reset`, `redirectTo` MUST equal:

```text
{dashboardOrigin}/tilbakestill-passord
```

Another path on a trusted origin is not accepted. A relative callback is not accepted.

The server-side dashboard action sets `Origin` from the incoming dashboard request. The backend trusted-origin policy remains authoritative.

The implementation MUST NOT disable Better Auth origin checks, CSRF checks, or the existing transport check.

## 8. Durable reset-mail outbox

Add one identity-owned relation named:

```text
auth.password_reset_email_outbox
```

Each row contains these semantic fields:

| Field | Contract |
| --- | --- |
| `effectId` | Stable unique effect identifier derived from the verification-row identifier |
| `verificationId` | Opaque reference to the Better Auth verification row |
| `subjectPersonId` | Canonical `PersonId` for the Better Auth user |
| `status` | Closed state from the list below |
| `attempts` | Non-negative delivery attempt count |
| `claimId` | Opaque worker claim identifier, nullable outside `Processing` |
| `claimedAt` | Claim timestamp, nullable outside `Processing` |
| `createdAt` | Authoritative enqueue timestamp |
| `deliveredAt` | Provider acknowledgement timestamp, nullable before delivery |
| `lastFailureCode` | Bounded closed failure code, nullable without a failure |

The closed status set is:

```text
Pending
Processing
Delivered
Failed
Quarantined
```

`verificationId` is unique. One Better Auth verification row can create at most one mail effect.

The outbox does not store an email address. The worker resolves the current Better Auth user email from `subjectPersonId`.

The outbox MUST NOT store these values:

- reset token
- password or password hash
- full reset URL
- callback URL
- session token or cookie
- raw request body or headers
- arbitrary provider payload

The raw token remains only in the Better Auth verification state and bounded process memory. The delivery adapter receives it only inside the supplied reset URL.

### 8.1 Enqueue ordering

Better Auth creates the verification row before it calls `sendResetPassword`.

`sendResetPassword` resolves that row and inserts the `Pending` outbox row. It also appends the known-user request audit in one owned transaction.

The callback returns only after that transaction commits. Better Auth background-task dispatch is not used for this callback.

Better Auth 1.7.1 catches callback failures. The outer handler MUST observe the callback outcome through bounded request-local coordination.

If the known-user enqueue fails, the outer handler replaces the false Better Auth success with a generic `503` response.

The failed verification row can remain until its one-hour expiry. It is never mailed and never exposed.

If no user exists, Better Auth does not call `sendResetPassword`. The outer handler appends one concealed request audit and returns the same normal `200` shape.

The public response does not disclose which branch occurred. It contains no email address or subject identifier.

### 8.2 Claim and delivery

A worker claims one eligible row with `FOR UPDATE SKIP LOCKED`. The claim changes `Pending` or `Failed` to `Processing`.

The claim increments `attempts` and sets `claimId` and `claimedAt`. A stale claim returns to `Pending` with a bounded failure code.

Before delivery, the worker proves these facts:

1. The verification row exists.
2. The identifier has the Better Auth reset-password form.
3. The verification value equals `subjectPersonId`.
4. The verification has not expired.
5. The Better Auth user still exists.

An invalid, expired, or mismatched effect becomes `Quarantined`. The worker does not call the provider.

The worker constructs the Better Auth reset URL in memory. It uses the configured canonical and dashboard origins.

The worker calls `PasswordResetMailDelivery` with `effectId` as the idempotency key. The worker owns retries, not the provider adapter.

A provider acknowledgement changes the row to `Delivered`. The same transaction writes `deliveredAt` and the delivery audit.

A typed transport failure changes the row to `Failed`. The same transaction writes the bounded failure code and failure audit.

The delivery model is at-least-once unless the selected provider proves idempotency. A crash after provider send can otherwise cause a duplicate email.

The implementation MUST NOT claim exactly-once delivery without provider evidence.

## 9. External authority capsule

The operator-approved capsule defines `PasswordResetMailDelivery` without putting credentials in this specification.

The authority accepts only this semantic input:

```ts
interface PasswordResetMailDeliveryRequest {
  readonly effectId: string;
  readonly recipientEmail: string;
  readonly resetUrl: string;
  readonly expiresAt: Date;
}
```

The authority returns only a bounded acknowledgement. It returns typed failures for rejection, unavailability, and timeout.

The operator capsule MUST define these facts:

1. The provider and owning account.
2. The runtime and deployment that hold the adapter.
3. The secret or binding injection mechanism.
4. The accepted sender identity.
5. The provider acknowledgement that means `Delivered`.
6. The idempotency guarantee for `effectId`.
7. The timeout and maximum request size.
8. The retryable and terminal failure classes.
9. The permitted recipient-data and provider-log retention.
10. The operational owner and incident path.

This amendment selects none of those values. It creates no credential, provider account, hostname, deployment, or remote resource.

The live adapter MUST NOT log the reset URL, token, recipient address, credential, body, or provider payload.

A local proof needs a real observable mailbox. A recording array, console output, or always-success adapter is not delivery evidence.

## 10. Failure and ordering semantics

The public forgot-password result is deliberately generic. The page uses this meaning:

> If the account exists, an email will arrive with reset instructions.

The page MUST NOT say that the system sent an email. A request response is not delivery evidence.

A known-user request is accepted only after its `Pending` row commits. A callback failure returns generic `503`.

A provider failure does not change the request response after that response exists. The durable worker retries the `Failed` row.

Better Auth consumes a reset token before password hashing and credential update. A later failure can consume the link without changing the password.

Better Auth updates the password before it deletes sessions. A later deletion failure can leave the password changed with old sessions present.

Therefore, a reset `5xx` result has an unknown final credential outcome. The page directs the user to request a new link.

A reset `200` result has the complete meaning from section 6. No weaker success is allowed.

This amendment makes no atomicity claim across these boundaries:

- Better Auth verification creation and outbox enqueue
- provider send and outbox completion
- password update and session deletion
- Better Auth state and append-only audit

The implementation must prove each observed ordering. Evidence must name every partial-failure result.

## 11. Identity security audit extension

0054.1 remains the audit schema authority. This amendment extends its closed `eventKind` set.

Add these event kinds:

```text
password-reset-request-accepted
password-reset-request-rejected
password-reset-mail-enqueue-failed
password-reset-mail-delivered
password-reset-mail-failed
password-reset-success
password-reset-failure
```

Use only bounded outcome codes. The minimum codes are:

| Event kind | Allowed minimum outcome codes |
| --- | --- |
| `password-reset-request-accepted` | `mail-enqueued`, `identity-undisclosed` |
| `password-reset-request-rejected` | `input-invalid`, `origin-not-trusted`, `redirect-not-allowed`, `rate-limited` |
| `password-reset-mail-enqueue-failed` | `outbox-unavailable` |
| `password-reset-mail-delivered` | `provider-acknowledged` |
| `password-reset-mail-failed` | `provider-rejected`, `provider-unavailable`, `delivery-timeout`, `verification-invalid`, `verification-expired`, `authority-mismatch` |
| `password-reset-success` | `password-updated-sessions-revoked` |
| `password-reset-failure` | `invalid-token`, `password-policy-rejected`, `engine-failure` |

A known-user enqueue event can contain `subjectPersonId`. An unknown-user request event keeps that field `null`.

A reset success event contains the established subject. It uses `password-updated-sessions-revoked` instead of an invented session count.

A reset failure contains the subject only when the request-local callback established it. It does not query or record the token.

Every request-bound event contains the 0054.1 request correlation. Request-local coordination uses that correlation and deletes its entry in `finally`.

The audit MUST NOT store these values:

- email address
- reset token or verification identifier
- password or password hash
- reset URL or callback URL
- session token or cookie
- raw body or headers
- provider response body or provider credential

The audit remains append-only. The outbox is mutable delivery state and does not replace the audit.

The known-user request audit and outbox enqueue share one owned transaction. They do not share the Better Auth verification transaction.

The delivery audit and outbox status update share one owned transaction. They do not share the provider transaction.

The reset audit occurs after the Better Auth handler result. Audit failure returns `503`, even when Better Auth state already changed.

Evidence MUST report that partial result. It MUST NOT describe the complete reset as atomic.

## 12. Dashboard contract

The forgot-password page validates that the email field is present. Better Auth remains the email-format authority.

The normal page result uses the generic text from section 10. Known and unknown accounts have the same visible result.

The native reset page has these states:

```text
Ready
Submitting
Succeeded
InvalidOrExpired
OutcomeUnknown
```

`Ready` requires a token query value. `InvalidOrExpired` covers a missing token and `error=INVALID_TOKEN`.

The password and confirmation fields use `autocomplete="new-password"`. The page checks equality and the 12-character minimum.

`Succeeded` redirects to:

```text
/login?reset=true
```

`OutcomeUnknown` explains that the link cannot be retried safely. It directs the user to request a new reset email.

The route never displays, logs, stores, or reports the token. Browser history contains the callback query by Better Auth design.

The browser action sends the token only in the Better Auth JSON body. Server logs and evidence filters must redact that body.

## 13. Required browser and database journey

Use a synthetic Better Auth user and disposable local state. The journey needs a real observable mailbox approved for local proof.

The journey performs these steps:

1. Create one Better Auth user with a valid credential.
2. Create two active sessions for that user.
3. Submit the known email on the forgot-password page.
4. Submit an unknown email and observe the same visible result.
5. Observe one `Pending` outbox row for the known user.
6. Observe no credential or mail effect for the unknown user.
7. Run the worker and observe provider acknowledgement.
8. Observe `Delivered` and the bounded delivery audit.
9. Read the email through the real local mailbox without copying its token into evidence.
10. Open the exact Better Auth callback URL.
11. Observe the dashboard redirect with the token query.
12. Submit a valid new password through the exact reset request.
13. Observe the login success page.
14. Use both old cookies on a protected native resource and observe `401`.
15. Try the old password and observe credential rejection.
16. Use the new password and create one new session.
17. Replay the reset link and observe `INVALID_TOKEN` without mutation.
18. Exercise an expired link and observe the invalid-link page.
19. Exercise a provider failure, durable retry, and later delivery.
20. Exercise an enqueue failure and observe generic `503`.
21. Inspect the append-only audit through an independent observer connection.
22. Assert that audit, outbox, logs, traces, and evidence contain no forbidden value.

The final native journey reaches no Symfony password route. The interim legacy journey must assert its retained boundary instead.

No proof uses a production credential, remote database, production recipient, or release deployment.

## 14. Dependency and cutover order

The dependency order is mandatory:

2. Obtain operator approval for the external authority capsule.
3. Freeze the password-cohort migration and release ownership.
4. Add the identity outbox and audit migration.
5. Implement the live delivery adapter and durable worker.
6. Prove delivery with a real local mailbox.
7. Configure Better Auth enqueue, one-hour expiry, and full session deletion.
8. Add `createPasswordRecoveryClient` outside the generated native client.
9. Migrate the two dashboard routes in one change.
10. Run the complete database and browser journey.
11. Remove the legacy server adapter and Symfony reset routes.
12. Obtain separate operator authority for release and deployment.

Steps 4 through 12 remain blocked until steps 2 and 3 are complete.

A caller migration cannot precede durable delivery. A credential-cohort migration cannot split sign-in and reset ownership.

## 15. Exact falsifiers

The contract is false if any condition below occurs:

1. A password-recovery operation enters `ExternalNativeApi` or `InternalNativeApi`.
2. The reflected count changes from 52 external operations and one internal operation.
3. A reset operation enters native OpenAPI, generated operations, or `native-api-operations.json`.
4. The implementation restores `createClient`, `client.auth`, `client.admin`, or another v0.1 namespace.
5. The interim dashboard uses a general Symfony client instead of the narrow server-only adapter.
6. A Symfony reset route is described as a native alias.
7. The released caller leaves Symfony before the delivery and cohort blockers close.
8. A cohort uses Symfony password reset with Better Auth sign-in.
9. `sendResetPassword` is absent, a no-op, logger-only, or recording-only in live composition.
10. A known-user `200` response has no committed `Pending` outbox row.
11. The page says that mail was sent before provider acknowledgement exists.
12. The callback URL is caller-selected, relative, wildcard-based, or another trusted-origin path.
13. The mail adapter builds a direct dashboard token URL instead of using the Better Auth URL.
14. The reset request uses `{ password, code }` instead of `{ newPassword, token }`.
15. The reset token enters the reset request query or dashboard action path.
16. The native dashboard keeps the dynamic `$code` route.
17. The dashboard keeps the eight-character password rule.
18. `resetPasswordTokenExpiresIn` is not exactly one hour.
19. `revokeSessionsOnPasswordReset` is absent or false.
20. An old session succeeds after a `200` reset response.
21. The old password succeeds after a `200` reset response.
22. A consumed reset link changes a credential or session on replay.
23. A forbidden value enters the outbox, audit, log, trace, or evidence.
24. A provider failure marks an outbox row `Delivered`.
25. A failed or stale claim has no durable recovery state.
26. The worker calls a provider for an invalid, expired, or mismatched verification row.
27. The implementation claims exactly-once delivery without provider idempotency evidence.
28. The implementation claims atomicity across a boundary excluded in section 10.
29. Audit failure after state mutation is hidden or reported as a clean rollback.
30. A local recording sink is presented as real mail delivery evidence.
31. The specification selects a provider, credential, account, deployment, or release action.

## 16. Definition of done

This specification is complete when all of these statements are true:

1. The amendment exists as one design-spec file at the exact source base.
2. Its status is a frozen contract with implementation blocked.
3. The two operator prerequisites are explicit.
4. The interim Symfony boundary is explicit and remains outside NativeApi.
5. The native request, callback, reset, origin, session, outbox, audit, and browser contracts are exact.
6. The external authority capsule has requirements but no selected provider or credential.
7. The 0077.2 operation count remains unchanged.
8. The falsifiers reject fake delivery, mixed credential ownership, compatibility namespaces, and false atomicity.
9. No implementation, test, build, generation, install, browser, network, database, reset, deployment, or release effect occurs.

Implementation completion is a later result. It requires the dependency order in section 14 and separate operator authority.

## 17. Explicit deferrals

This amendment does not select or perform these items:

- provider selection or account creation
- credential creation, storage, or rotation
- production hostname or deployment selection
- production data access or password migration execution
- remote mailbox, database, or provider access
- release, deployment, or DNS action
- 2FA, passkeys, SSO, social providers, or impersonation
- personal access tokens or standalone API keys
- a general notification platform
- a change to any NativeApi resource or operation count

Those items require their own authority and evidence. They MUST NOT enter implementation as an undocumented fallback.
