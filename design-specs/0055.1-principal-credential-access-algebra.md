## 1. Amendment boundary

This amendment freezes one semantic model for principals, credentials, scopes, capabilities, requirements, exposure, and decision time.

This amendment is limited to the authority algebra foundation. It does not freeze the complete route matrix or an OAuth protocol.

Specification 0055 remains authoritative for person-keyed Organization and Economy facts. This amendment generalizes the decision input without moving those facts.

Specification 0054.1 remains authoritative for Better Auth and first-party browser sessions. This amendment does not change its cookie or session decisions.

The 0055.1 implementation MUST use one clean cutover for its algebra, scope migration, and internal isolation. It MUST NOT cut over the external operation matrix.

Within that boundary, it MUST NOT add an alias, compatibility decoder, default `AccessSpec`, placeholder metadata, dual registry, or fallback principal.

## 3. Frozen identifiers and schemas

All identifiers below are branded values. A decoder rejects an empty, malformed, or unknown registered identifier.

| Identifier           | Meaning                            | Registry rule                                   |
| -------------------- | ---------------------------------- | ----------------------------------------------- |
| `PersonId`           | Canonical human identity           | Existing Organization and Identity contract     |
| `ServicePrincipalId` | Canonical non-human principal      | Closed service-principal registry and authority |
| `CapabilityId`       | One object-capability instance     | Owning domain capability authority              |
| `CapabilityTypeId`   | One authorization action type      | Closed `CAPABILITY_TYPES` registry              |
| `RequirementId`      | One typed decision precondition    | Closed `REQUIREMENT_TYPES` registry             |
| `DomainId`           | One authority domain               | Closed `DOMAIN_IDS` registry                    |
| `ResourceKind`       | One canonical resource type        | Closed `RESOURCE_KINDS` registry                |
| `ResourceId<K>`      | One resource identity for kind `K` | Decoder registered for `K`                      |
| `ScopeResolverId`    | One canonical context resolver     | Closed `SCOPE_RESOLVERS` registry               |

Operator data cannot create an identifier in these registries. A new registry entry requires a frozen contract change and source change.

### 3.1 Principal schema

```ts
type Principal =
  | { readonly _tag: "Anonymous" }
  | { readonly _tag: "Person"; readonly personId: PersonId }
  | {
      readonly _tag: "ServicePrincipal";
      readonly servicePrincipalId: ServicePrincipalId;
    }
  | { readonly _tag: "CapabilityHolder"; readonly capabilityId: CapabilityId };

type PrincipalKind = Principal["_tag"];
```

A principal states who acts. It does not contain a role, grant, scope, membership, token, credential value, or authorization verdict.

`Person` keeps the canonical `PersonId` from specifications 0054.1 and 0055. `ServicePrincipal` is not a synthetic person.

`CapabilityHolder` identifies one object-capability instance. It is not the person or service that received the capability bytes.

### 3.2 Credential-mechanism schema

```ts
type CredentialMechanism<K extends CapabilityTypeId = CapabilityTypeId> =
  | { readonly _tag: "None" }
  | { readonly _tag: "BetterAuthCookie" }
  | { readonly _tag: "OAuthUserBearer" }
  | { readonly _tag: "OAuthServiceBearer" }
  | { readonly _tag: "ObjectCapability"; readonly capabilityType: K };
```

A credential mechanism states how the transport authenticates a principal. It does not grant endpoint access by itself.

| Mechanism             | Successful principal                   | Owning resolver                    | Frozen limit                                         |
| --------------------- | -------------------------------------- | ---------------------------------- | ---------------------------------------------------- |
| `None`                | `Anonymous`                            | No credential resolver             | It is the sole mechanism for an anonymous operation. |
| `BetterAuthCookie`    | `Person(PersonId)`                     | Better Auth through `Identity`     | First-party browser sessions only                    |
| `OAuthUserBearer`     | `Person(PersonId)`                     | OAuth authority                    | Mechanics and lifetimes are deferred to 0082.        |
| `OAuthServiceBearer`  | `ServicePrincipal(ServicePrincipalId)` | OAuth authority                    | Mechanics and lifetimes are deferred to 0082.        |
| `ObjectCapability<K>` | `CapabilityHolder(CapabilityId)`       | Owning object-capability authority | The resolved record has capability type `K`.         |

For a protected operation, the request MUST supply exactly one accepted credential mechanism. Missing, malformed, invalid, expired, revoked, wrong-kind, and ambiguous credentials are credential failures.

Two supplied accepted mechanisms are ambiguous. The transport MUST NOT choose one by header order, cookie order, or a fixed precedence.

An anonymous operation does not resolve ambient credentials. A supplied cookie or bearer cannot change its representation or access decision.

Only the owning credential resolver can read credential bytes. Downstream code receives the principal and bounded non-secret credential evidence.

### 3.3 Credential outcome

```ts
type CredentialFailureReason =
  | "Missing"
  | "Malformed"
  | "Invalid"
  | "Expired"
  | "Revoked"
  | "WrongMechanism"
  | "AmbiguousMechanism";

type CredentialOutcome =
  | {
      readonly _tag: "Accepted";
      readonly mechanism: CredentialMechanism;
      readonly principal: Principal;
      readonly evidenceRef: CredentialEvidenceRef;
    }
  | { readonly _tag: "Rejected"; readonly reason: CredentialFailureReason };
```

`CredentialEvidenceRef` is a bounded, non-secret reference. It cannot contain a cookie, token, raw header, password, or reconstructible credential.

## 4. First-party Better Auth preservation

`BetterAuthCookie` preserves specification 0054.1 without alteration. Better Auth 1.7.1 remains the credential and first-party session engine.

The 0055.1 implementation MUST preserve these decisions from `design-specs/0054.1-native-identity-session-hardening.md:33-79`:

1. `auth.user.id` is the canonical `PersonId`.
2. The `auth` schema contains no role, grant, scope, department, capability, or policy authority.
3. The cookie is not an OAuth bearer, object capability, service credential, or general API token.
4. Authoritative session resolution uses current persisted state and no `cookieCache` grace period.
5. The cookie remains `HttpOnly`, `SameSite=Lax`, `Path=/`, and environment-appropriate `Secure`.
6. Better Auth secure-prefix behavior remains intact.
7. Session expiry remains seven days and update age remains one day.
8. No response or evidence artifact exposes reusable credential material.

This amendment does not rename or replace the six session resources frozen by 0054.1. It does not weaken its CSRF or trusted-origin contract.

## 5. Capability, grant, role, and requirement algebra

### 5.1 Typed capabilities

```ts
type Capability<K extends CapabilityTypeId = CapabilityTypeId> = {
  readonly type: K;
};

type CapabilityExpression =
  | { readonly _tag: "None" }
  | { readonly _tag: "One"; readonly capability: Capability }
  | { readonly _tag: "All"; readonly capabilities: NonEmptyReadonlyArray<Capability> }
  | { readonly _tag: "Any"; readonly capabilities: NonEmptyReadonlyArray<Capability> };
```

`CapabilityTypeId` is a closed branded identifier. Unknown capability types fail during decode, endpoint registration, grant composition, and OpenAPI generation.

`None` is valid only when the operation needs no authorization capability. `All` and `Any` reject empty collections and duplicate capability types.

A capability type names an action. It does not name a principal, role, scope, credential, route prefix, or HTTP method.

### 5.2 Grants and role macros

```ts
type Grant<K extends CapabilityTypeId = CapabilityTypeId> = {
  readonly grantId: GrantId;
  readonly subject: Exclude<Principal, { readonly _tag: "Anonymous" }>;
  readonly capability: Capability<K>;
  readonly scope: Scope;
  readonly startAt: AuthorizationInstant;
  readonly endAt: AuthorizationInstant | null;
  readonly requirements: ReadonlyArray<TypedRequirement>;
  readonly source: AuthorityRef;
  readonly revision: Revision;
};
```

A grant is a candidate capability contribution. A grant is active only in the half-open interval `[startAt, endAt)`.

Semantically, a persisted grant is a one-contribution macro. Its presence alone is never an access verdict.

A role is a named macro over canonical authority facts. A grant-authoring rule is also a macro over canonical facts and rule state.

A macro can contribute candidate grants. It cannot return `Allow`, remove a requirement, rewrite context, or select a decision mode.

A global administrator role can contribute broad grants. It still cannot bypass ownership, relationship, resource state, time, scope, transaction, or endpoint requirements.

A team-leader role can contribute department-scoped grants. It does not infer the department from an `/admin` path or a role name.

Object-capability resolution contributes a grant for its `CapabilityHolder`. That grant retains its type, scope, interval, state, and typed requirements.

### 5.3 Typed requirements

```ts
type TypedRequirement<K extends RequirementId = RequirementId, P = RequirementParameters<K>> = {
  readonly id: K;
  readonly parameters: P;
};

type RequirementResult<K extends RequirementId = RequirementId> =
  | { readonly id: K; readonly _tag: "Satisfied" }
  | { readonly id: K; readonly _tag: "Failed"; readonly reason: RequirementReason<K> };
```

`REQUIREMENT_TYPES` maps each requirement ID to one parameter schema, one context schema, and one evaluator. Operator data cannot supply executable logic.

Requirements express ownership, relationship, resource state, active windows, and other domain preconditions. Every listed operation and grant requirement MUST be satisfied.

Requirement composition is conjunctive. Duplicate identical requirements collapse. Conflicting parameters fail closed as `Ambiguous`.

A grant or role can add requirements. It cannot remove, weaken, negate, or replace an endpoint requirement.

Specification 0056.2 will decide how declarative rules author parameter fills and requirements. This amendment does not broaden the current rule decoder.

### 5.4 Decision law

For a non-anonymous principal, access is allowed exactly when all applicable terms below are true:

1. One accepted credential resolves the required principal kind.
2. The canonical scope resolver returns a valid resolution.
3. The required capability expression is satisfied by active candidate grants for each allowed context.
4. Each used grant scope matches its canonical context.
5. Each grant is active at the one authorization instant.
6. Every endpoint requirement is satisfied for each allowed context.
7. Every used grant requirement is satisfied for each allowed context.
8. The evaluation uses the endpoint decision mode.

A role name, route segment, valid credential, or `Global` scope cannot replace any term in this law.

For `Anonymous`, access is allowed only when the `AccessSpec` uses `None`, principal kind `Anonymous`, and capability expression `None`.

## 6. Scope algebra

### 6.1 Schema

```ts
type ResourceRef<K extends ResourceKind = ResourceKind> = {
  readonly kind: K;
  readonly id: ResourceId<K>;
};

type Scope =
  | { readonly _tag: "Global" }
  | { readonly _tag: "Domain"; readonly domainId: DomainId }
  | { readonly _tag: "Department"; readonly departmentId: DepartmentId }
  | { readonly _tag: "Resource"; readonly resource: ResourceRef }
  | { readonly _tag: "And"; readonly left: Scope; readonly right: Scope }
  | { readonly _tag: "Or"; readonly left: Scope; readonly right: Scope };

const RECEIPT_DOMAIN_ID = DomainId.make("receipts");
```

There is no `Tenant` scope. There is no domain-specific `Receipt` scope variant.

The legacy `Receipt` rule scope maps to `Domain(DomainId("receipts"))` during the clean migration. The new decoder never accepts `Receipt`.

### 6.2 Meaning

| Scope            | Match against canonical context                                      |
| ---------------- | -------------------------------------------------------------------- |
| `Global`         | Always matches the context for the same capability type.             |
| `Domain(D)`      | Matches only when `context.domainId` equals `D`.                     |
| `Department(D)`  | Matches only when `context.departmentId` exists and equals `D`.      |
| `Resource(K, R)` | Matches only when the target resource kind and ID equal `K` and `R`. |
| `And(A, B)`      | Matches only when both `A` and `B` match.                            |
| `Or(A, B)`       | Matches when `A`, `B`, or both match.                                |

Domain and Department are separate axes. A department does not imply a domain, and a domain does not imply a department.

`Global` is the top scope for one capability type. It is not a wildcard capability and does not satisfy another capability type.

`And` and `Or` are associative, commutative, and idempotent. Registration normalizes child order and removes identical children for deterministic evidence.

An empty `And` or `Or` does not exist. Recursive scopes have a finite decoder depth and a bounded encoded size.

### 6.3 Canonical resource context

```ts
type CanonicalResourceContext<C = unknown> = {
  readonly domainId: DomainId;
  readonly departmentId: DepartmentId | null;
  readonly resource: ResourceRef | null;
  readonly facts: C;
  readonly authorityVersion: AuthorityVersion;
};

type CanonicalScopeResolution<C = unknown> = {
  readonly selection: "ExactlyOne" | "AllMatching";
  readonly contexts: ReadonlyArray<CanonicalResourceContext<C>>;
};

type ScopeResolver<I, C> = (
  input: I,
  principal: Principal,
  instant: AuthorizationInstant,
  mode: AuthorizationMode,
) => Effect<CanonicalScopeResolution<C>, ScopeResolutionError, AuthorityServices>;
```

The `facts` field uses a resolver-specific typed schema. It can contain ownership, relationship, state, window, and version evidence.

A resolver ID points to one source implementation and one resolution schema. The implementation and endpoint declaration share the same type parameter.

The resolver gets decoded endpoint input. Client input can identify or narrow a candidate resource, department, or relationship.

Client input cannot create authority. The resolver compares input with canonical state and fails closed on a mismatch.

For an existing resource, the resource record and its canonical parent records select the domain and department. A caller-supplied department cannot replace them.

For a creation command, the endpoint fixes the domain. Canonical referenced records and validated target fields select the department before the decision.

An item or command resolver uses `ExactlyOne` and returns one context. A missing or duplicate canonical target fails before authorization.

A collection resolver uses `AllMatching`. It returns every canonical candidate context in stable order and never selects the first membership.

The evaluator applies capabilities, scopes, and requirements to all candidate contexts. The domain query receives the complete allowed context set.

For a non-anonymous principal, `AllMatching` MUST retain at least one context. Zero allowed contexts produce a typed authorization denial.

An anonymous collection can return an empty allowed context set. Its public projection cannot vary with ambient credentials.

A path segment such as `admin`, `me`, `internal`, or a role name supplies no authority fact. Route shape never infers principal kind, capability, or scope.

A resolver MUST NOT read a role from the credential. It MUST NOT use membership order, a fallback department, or an earlier-request projection.

## 7. Authorization instant and decision mode

```ts
type AuthorizationMode = "SnapshotRead" | "Transaction";
```

Each access evaluation captures one `AuthorizationInstant`. Credential state, context, grants, rules, requirements, and decision use that instant.

| Mode           | Required behavior                                                                                                                          | Forbidden behavior                                                                      |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------- |
| `SnapshotRead` | Resolve the credential, principal, context, and authority from one consistent read snapshot. Return the projection from that journey.      | Mixed snapshots, cached roles, earlier-request actors, and write effects                |
| `Transaction`  | Resolve the credential, principal, and context, lock relevant rows, decide, transition state, and record owned effects in one transaction. | Pre-transaction verdicts, stale grants, unlocked authority rows, and reused retry facts |

The transport can extract a credential and parse its cryptographic envelope before the selected journey. That work cannot produce the authoritative outcome.

The authoritative credential outcome occurs inside the selected snapshot or transaction. Local revocation, client, token, session, and capability state is read there.

A transaction denial performs no domain transition, audit success, outbox append, or idempotency success write. Specification 0080.1 owns final HTTP idempotency details.

A retry captures a new instant and recalculates all authority. It never reuses the principal evidence, context, grant set, requirements, or decision from a failed attempt.

## 8. Access decision and concealment

```ts
type AccessDenialStage = "PrincipalKind" | "Capability" | "Scope" | "Requirement";

type AccessDecision<C> =
  | {
      readonly _tag: "Allow";
      readonly principal: Principal;
      readonly resolution: CanonicalScopeResolution<C>;
      readonly authorizationInstant: AuthorizationInstant;
    }
  | {
      readonly _tag: "Deny";
      readonly stage: AccessDenialStage;
      readonly reason: AccessDenialReason;
    };

type ConcealmentPolicy =
  | { readonly _tag: "Reveal" }
  | {
      readonly _tag: "NotFound";
      readonly conceal: NonEmptyReadonlyArray<
        "CredentialFailure" | "PrincipalKind" | "Capability" | "Scope" | "Requirement"
      >;
    };
```

Credential rejection occurs before `AccessDecision`. It is not an authenticated authorization denial.

The HTTP adapter applies this exact mapping:

| Outcome                                       |        Default HTTP status | Exception                                                |
| --------------------------------------------- | -------------------------: | -------------------------------------------------------- |
| Credential failure                            |                        401 | An explicit `NotFound` concealment entry maps it to 404. |
| Denial for a resolved non-anonymous principal |                        403 | An explicit matching concealment entry maps it to 404.   |
| External request for an internal-only route   | Normal route-not-found 404 | This is routing isolation, not concealment.              |
| Canonical resource absence                    |        404 resource result | It is not a credential or authorization result.          |

Only credential failure can produce 401. Missing capability, wrong scope, inactive authority, failed ownership, and failed state requirements never produce 401.

Concealment changes only the external projection. Internal tracing and security audit data retain the safe denial stage without credential material.

A concealment policy is exhaustive and endpoint-local. A path prefix, group name, error mapper, or transport default cannot imply it.

Infrastructure failure is not a credential or authorization denial. Specification 0080.1 owns its final HTTP representation.

## 9. Endpoint `AccessSpec`

### 9.1 Exhaustive schema

```ts
type Exposure = "External" | "Internal";

type AccessSpec<I, C> = {
  readonly exposure: Exposure;
  readonly acceptedCredentials: NonEmptyReadonlyArray<CredentialMechanism>;
  readonly principalKinds: NonEmptyReadonlyArray<PrincipalKind>;
  readonly capabilities: CapabilityExpression;
  readonly requirements: ReadonlyArray<TypedRequirement>;
  readonly canonicalScopeResolver: ScopeResolverId;
  readonly concealment: ConcealmentPolicy;
  readonly decisionTime: AuthorizationMode;
};
```

The final target invariant is one exact `AccessSpec` beside every Vektor-owned endpoint. Specification 0077.2 owns that complete external assignment.

The 0055.1 implementation owns the typed annotation constructor, reflection key, decoder, evaluator binding, and deterministic projector.

For an endpoint that uses this constructor, every field is required. Construction fails when a field is absent, an array is invalid, or a registry reference is unknown.

There is no default, optional fallback, inferred value, or placeholder `AccessSpec`. A separate operation-to-access map is forbidden.

After 0055.1, the existing external endpoint composition remains pre-cutover. It cannot claim exhaustive `AccessSpec` coverage.

Specification 0055.1 MUST NOT assign access metadata to the complete external matrix. Specification 0077.2 performs that atomic cutover.

`principalKinds` is explicit even though credentials imply principal kinds. Registration rejects a mismatch between these two fields.

`None` MUST be the only accepted credential when `principalKinds` is exactly `Anonymous`. That combination requires capability expression `None`.

Each non-`None` mechanism MUST map to at least one listed principal kind. Each listed non-anonymous principal kind MUST have an accepted mechanism.

An `ObjectCapability<K>` mechanism MUST reference capability type `K` in its capability expression. It cannot unlock an unrelated capability.

The resolver output schema MUST satisfy every requirement context schema. Endpoint registration fails before router construction when they differ.

A converted handler receives one allowed `AccessContext`. It does not resolve a second actor, choose a role from a path, or repeat credential precedence.

Domain commands retain their invariant checks. The access layer cannot make an invalid domain transition valid.

## 10. Exposure and router construction

`External` and `Internal` describe reachability. They are not capabilities and do not replace endpoint authorization.

The 0055.1 implementation MUST construct these independent roots:

```text
ExternalNativeApi -> ExternalNativeRouter -> external native ingress
InternalNativeApi -> InternalNativeRouter -> explicit internal evidence ingress
```

After 0055.1, `ExternalNativeApi` contains the existing external endpoints and no internal endpoint. Its access wiring remains pre-cutover until 0077.2.

`InternalNativeApi` contains only the receipt evidence operation with the exact `Internal` assignment in section 9.3.

After 0077.2, every endpoint in `ExternalNativeApi` has `AccessSpec.exposure` equal to `External`.

The external handler graph MUST NOT contain, mount, fall through to, or dispatch to the internal router. Knowing an internal path cannot make it reachable.

The internal router has its own complete handler construction. Its endpoints still require credentials, principals, capabilities, requirements, scopes, and decision modes.

An internal listener or test ingress receives the internal router explicitly. No public path named `internal` or `e2e` is an access boundary.

The current receipt evidence operation moves to `InternalNativeApi`. OpenAPI exclusion alone is not sufficient.

Better Auth `/api/auth/*` remains an external credential-engine surface outside both native resource API roots. It is not copied into either root.

This amendment does not choose a production internal listener, hostname, account, or network policy. Those choices require operator authority.

## 11. Decision flow

This flow applies to each endpoint converted to the new machinery. Specification 0055.1 proves it with bounded declarations and the internal evidence operation.

Pre-cutover external endpoints retain their current flow. Specification 0077.2 moves all of them to this flow atomically.

```text
request
  |
  v
select constructed ingress and match endpoint
  |
  v
read the endpoint's sole AccessSpec
  |
  v
capture one AuthorizationInstant and enter SnapshotRead or Transaction
  |
  v
resolve exactly one accepted credential inside that journey
  | rejected ------------------------------> 401 or explicit concealed 404
  v
Principal
  |
  v
run the named canonical scope resolver
  |
  v
read direct authority facts, grants, roles, tags, and applicable rules
  |
  v
expand macros into typed candidate grants
  |
  v
evaluate principal kind + capability + time + scope + requirements
  | denied --------------------------------> 403 or explicit concealed 404
  v
Allow(Principal, CanonicalScopeResolution, AuthorizationInstant)
  |
  +--> SnapshotRead: produce the projection from the same snapshot
  |
  +--> Transaction: perform the state transition and owned transaction effects
```

No stage reads a verdict from a credential, session, role, rule row, route prefix, or earlier request.

## 13. OpenAPI generation contract

`OpenApi.fromApi(ExternalNativeApi)` remains the only native public OpenAPI source. The internal API root is never an input to public generation.

Specification 0055.1 implements a deterministic projector for any endpoint that carries an `AccessSpec`. The projector emits this `x-vektor-access` shape:

```json
{
  "exposure": "External",
  "acceptedCredentials": ["BetterAuthCookie", "OAuthUserBearer"],
  "principalKinds": ["Person"],
  "capabilities": {
    "all": ["receipt.approve"]
  },
  "requirements": [{ "id": "receipt.pending" }, { "id": "receipt.approver-relationship" }],
  "canonicalScopeResolver": "receipt.by-id",
  "concealment": { "mode": "Reveal", "stages": [] },
  "decisionTime": "Transaction"
}
```

The 0055.1 implementation proves this projection with bounded proof declarations. Those declarations are not native routes or public OpenAPI operations.

Until 0077.2, the public OpenAPI artifact remains pre-cutover. It MUST NOT claim exhaustive `AccessSpec` or `x-vektor-access` coverage.

Specification 0055.1 MUST NOT emit a default or placeholder extension for an unconverted external endpoint.

After the atomic 0077.2 cutover, each external operation emits one `x-vektor-access` value from its sole exact `AccessSpec`.

The JSON shape is deterministic. Arrays that represent sets use normalized registry order.

OpenAPI `security` describes credential mechanisms only:

| Accepted mechanism    | OpenAPI projection                                                      |
| --------------------- | ----------------------------------------------------------------------- |
| `None`                | Empty operation security requirement. No `None` security scheme exists. |
| `BetterAuthCookie`    | First-party cookie header security scheme                               |
| `OAuthUserBearer`     | OAuth user-bearer security scheme defined by 0082                       |
| `OAuthServiceBearer`  | OAuth service-bearer security scheme defined by 0082                    |
| `ObjectCapability<K>` | The registered object-capability security scheme for `K`                |

Multiple accepted non-`None` mechanisms generate OpenAPI alternatives. The generated array expresses OR, not precedence.

OpenAPI `security` MUST NOT contain roles, grants, capability types, requirement IDs, scopes, resolver IDs, exposure, or decision time.

`x-vektor-access` MUST NOT contain credential bytes, live grant rows, person data, resolver output, authority versions, or decision evidence.

The 0055.1 machinery MUST reject these conditions:

1. A converted endpoint has multiple `AccessSpec` annotations.
2. An `AccessSpec` field is absent or uses an unknown registry ID.
3. Credentials and principal kinds are inconsistent.
4. `None` is mixed with another credential.
5. An object-capability type and capability expression are inconsistent.
6. A resolver output schema cannot satisfy a requirement input schema.
7. An internal endpoint occurs in `ExternalNativeApi` or public OpenAPI.
8. An external endpoint occurs in `InternalNativeApi`.
9. A Better Auth resource occurs in either native API root.
10. Projected OpenAPI `security` contains authorization semantics.
11. `x-vektor-access` differs from its runtime `AccessSpec`.
12. A second route-to-access registry exists.

Specification 0055.1 MUST NOT enable the repository-wide gate that rejects an external endpoint with no `AccessSpec`.

Specification 0077.2 enables that final gate in the same atomic change that assigns every external endpoint. The gate rejects missing or multiple metadata.

Existing route and operation reflection remains derivative. Both amendments extend current reflection without a handwritten route or access list.

Specification 0079 continues to own generated-reference provenance and drift gates. Specification 0080 continues to own primary reference information architecture.

## 15. Focused access tracer journey

The matching 0055.1 implementation adds one bounded tracer journey. It uses proof-only declarations, synthetic personas, disposable state, one real Better Auth cookie, and one real object capability.

The trace records only non-secret bounded fields:

```ts
type AccessTrace = {
  readonly declarationId: string;
  readonly exposure: Exposure;
  readonly credentialMechanism: CredentialMechanism["_tag"];
  readonly credentialOutcome: "Accepted" | "Rejected";
  readonly principalKind: PrincipalKind | null;
  readonly scopeResolverId: ScopeResolverId | null;
  readonly domainId: DomainId | null;
  readonly departmentId: DepartmentId | null;
  readonly resourceKind: ResourceKind | null;
  readonly decisionTime: AuthorizationMode | null;
  readonly capabilityOutcome: "Satisfied" | "Failed" | null;
  readonly failedRequirementIds: ReadonlyArray<RequirementId>;
  readonly decision: "Allow" | "Deny" | null;
  readonly projectedStatus: number;
};
```

The trace MUST NOT record a cookie, bearer, object-capability value, raw header, password, grant secret, or reconstructible credential.

The proof declarations have no native path or operation ID. They do not enter `ExternalNativeApi`, public OpenAPI, or a route registry.

The journey performs these exact observations in order:

1. Evaluate one anonymous proof declaration. The trace shows `None`, `Anonymous`, `SnapshotRead`, and `Allow`.
2. Resolve the real Better Auth cookie and evaluate one protected-read declaration. The trace shows `Person` and one canonical snapshot.
3. Evaluate a wrong department selector with the same principal. Canonical state wins and the projected result is 403, not 401.
4. Evaluate a representative receipt transaction with a valid scoped grant. The canonical resolver returns `Allow` before one disposable transition.
5. End that grant before a retry. The retry recalculates authority and returns 403 without another transition.
6. Evaluate an object-capability declaration with an invalid capability. Its explicit concealment projects 404.
7. Evaluate it with a valid capability. The trace shows `CapabilityHolder`, the exact capability type, and `Allow`.
8. Call the internal evidence path through the external ingress. The external router returns route-not-found 404 without an access trace.
9. Call the same operation through the explicit internal ingress with its accepted owner credential. The trace shows `Internal` and its full decision.
10. Project the bounded declarations. Each result has deterministic `x-vektor-access` and credential-only `security`.

The journey does not generate or modify the public external access matrix. It uses no OAuth route or bearer issuance.

Type-level and schema evidence cover OAuth credential variants until 0082 implements their mechanics.
