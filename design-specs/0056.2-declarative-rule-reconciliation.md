## 1. Amendment boundary

This amendment retains the global `delegate | parameter | requirement` rule-effect algebra from specification 0056.

It freezes the smaller set of rule variants that current capability functions can accept. The closed set has no parameter-rule variant.

This amendment also freezes requirement compilation, canonical context use, persistence migration, and per-receipt evaluation.

The following 0056 laws remain unchanged:

1. A rule is authority data, not executable policy.
2. A rule contributes algebra input. It never stores or returns an access verdict.
3. Rule intervals and tag-assignment intervals are half-open.
4. Subject, time, capability, and scope applicability use one authorization instant.
5. Existing delegate effects retain their current evidence shapes and behavior.
6. A command evaluates rules in the transaction that owns its state transition.
7. A retry reads new authority facts and uses a new instant.
8. Zero applicable rules preserve the direct-authority result.

Amendment 0056.1 records implementation evidence only. It changes no product contract (`design-specs/0056-declarative-authorization-rules.md:15-19`).

If 0056 conflicts with this document about parameter or requirement effects, this document controls.

Specification 0055.1 controls principals, credentials, scopes, canonical contexts, requirements, decision time, and access decisions.

## 2. Source evidence and unresolved mismatch

The observations in this section cite the source at the frozen base revision.

1. The global effect-kind schema already contains `delegate`, `parameter`, and `requirement` (`packages/domain/src/authz/schema.ts:29-37`).
2. `CAPABILITY_IDS` declares no parameter or requirement slot. It accepts only the current delegate variants (`packages/domain/src/authz/schema.ts:46-73`).
3. The closed `AuthzRuleSchema` currently decodes only two `approveReceipt` delegates and one `submitReceipt` delegate (`packages/domain/src/authz/schema.ts:123-159`).
4. The current generic requirement value contains caller-supplied `satisfied: boolean` (`packages/domain/src/authz/rules.ts:177-205`).
5. The current compiler accepts caller-supplied requirements and parameter fills (`packages/domain/src/authz/rules.ts:213-216`).
6. The current compiler creates an unregistered `ReceiptDepartmentResolved` Boolean result (`packages/domain/src/authz/rules.ts:249-310`).
7. The final composition trusts those Boolean values when it returns `RequirementFailed` (`packages/domain/src/authz/rules.ts:337-347`).
8. Specification 0055.1 instead registers `receipts.pending` and `receipts.approver-relationship` as typed requirements (`packages/domain/src/authz/access.ts:105-119`).
9. Their registry entries use an empty parameter schema and a canonical receipt context (`packages/domain/src/authz/access.ts:278-369`).
10. The registry derives `NotPending` and `NotApprover` from canonical facts. It does not accept a Boolean verdict (`packages/domain/src/authz/access.ts:335-350`).
11. The current approval collection decides global or department visibility before it reads the final receipt rows (`packages/domain/src/receipt/approval-list.ts:39-121`).

13. Approval commands currently supply only domain and department request scope to rule composition (`packages/domain/src/receipt/postgres.ts:772-802`).
14. Current writes decode before insertion. Current reads decode the complete persisted row and fail on an invalid row (`packages/domain/src/authz/postgres.ts:102-159`, `197-203`, `411-416`, and `459-504`).
15. Migration 0025 already maps the old `Receipt` scope to `Domain("receipts")` and removes the old scope shape (`packages/database/migrations/0025-principal-credential-access-algebra.sql:1-25`).

Items 4 through 7 are not a second supported requirement API. They are the mismatch that this amendment removes.

Items 11 through 13 cannot evaluate resource-state or relationship requirements correctly. They do not have one canonical context per receipt.

## 3. Frozen rule-effect algebra

The global vocabulary remains closed:

```ts
type AuthzRuleEffectKind = "delegate" | "parameter" | "requirement";
```

The vocabulary states the meaning of an effect. It does not make every capability-and-effect pair legal.

| Effect | Semantic contribution | Verdict authority |
| --- | --- | --- |
| `delegate` | One existing typed authority fact in a declared receptive evidence slot | None |
| `parameter` | One value in a declared parameter slot | None |
| `requirement` | One registered `TypedRequirement` added to the conjunctive requirement set | None |

A capability declaration closes the legal cross-product. Operator data cannot add a slot, effect, or requirement ID.

### 3.1 Exact capability declarations

The target declaration has these exact semantics:

```ts
const CAPABILITY_IDS = {
  approveReceipt: {
    receptiveEvidenceSlots: [
      "EconomyDepartmentApprovalGrant",
      "EconomyGlobalReceiptApprovalGrant",
    ],
    parameterSlots: [],
    requirementSlots: [
      "receipts.pending",
      "receipts.approver-relationship",
    ],
    acceptedEffects: ["delegate", "requirement"],
  },
  submitReceipt: {
    receptiveEvidenceSlots: ["EconomyPaymentAuthority"],
    parameterSlots: [],
    requirementSlots: [],
    acceptedEffects: ["delegate"],
  },
  reviewApplicants: {
    receptiveEvidenceSlots: [],
    parameterSlots: [],
    requirementSlots: [],
    acceptedEffects: [],
  },
} as const;
```

The array order above is canonical registry order. It is not operator-controlled priority.

### 3.2 Closed acceptance matrix

| Capability | Effect | Exact `params` JSON | Result |
| --- | --- | --- | --- |
| `approveReceipt` | `delegate` | `{"slot":"EconomyDepartmentApprovalGrant"}` | Accepted |
| `approveReceipt` | `delegate` | `{"slot":"EconomyGlobalReceiptApprovalGrant"}` | Accepted |
| `approveReceipt` | `requirement` | `{"requirementId":"receipts.pending","parameters":{}}` | Accepted |
| `approveReceipt` | `requirement` | `{"requirementId":"receipts.approver-relationship","parameters":{}}` | Accepted |
| `submitReceipt` | `delegate` | `{"slot":"EconomyPaymentAuthority","paymentAccountCiphertext":"<trimmed-nonempty>"}` | Accepted |
| `submitReceipt` | `parameter` or `requirement` | Any value | Rejected |
| `reviewApplicants` | Any effect | Any value | Rejected |
| Any current capability | `parameter` | Any value | Rejected |

There are zero legal parameter-rule variants. No current capability has a warranted parameter slot.

The generic parameter algebra remains defined. A future parameter rule requires a new frozen capability declaration and migration.

`submitReceipt` retains its existing delegate-only `EconomyPaymentAuthority` shape. Its ciphertext field and authority behavior do not change.

`reviewApplicants` remains a registered capability ID with no rule-receptive effect. No `AuthzRule` union member exists for it.

### 3.3 Requirement payload mapping

A decoded requirement rule maps its `params` value as follows:

```ts
const requirement: TypedRequirement = {
  id: rule.params.requirementId,
  parameters: rule.params.parameters,
};
```

The rule never contains `satisfied`, `reason`, `decision`, `allow`, or `deny`.

A requirement rule adds a precondition. It does not contribute an approval grant and cannot satisfy `approveReceipt` by itself.

## 4. Strict schemas and JSON laws

Every authored rule, persisted row projection, and backfill rule MUST use the same closed `AuthzRule` decoder.

The decoder uses `onExcessProperty: "error"` at the outer object and at every nested object.

These laws are exact:

1. The common rule fields remain `ruleId`, `capabilityId`, `effectKind`, `subject`, `scope`, `params`, `startAt`, `endAt`, and `revision`.
2. A `Person` subject contains only `_tag` and `personId`.
3. A `Tag` subject contains only `_tag` and `tagId`.
4. A rule scope contains only the keys declared for its variant.
5. A delegate `params` object contains only the keys in section 3.2.
6. A requirement `params` object contains only `requirementId` and `parameters`.
7. The `parameters` value for both accepted requirements is exactly an empty object.
8. An empty array, `null`, a Boolean, or an object with one extra key is not an empty requirement-parameter object.
9. An unknown capability, effect, slot, requirement ID, subject variant, or scope variant fails decode.
10. A known value in an unsupported capability-and-effect combination fails decode.
11. A `satisfied` key fails decode at every nesting level.
12. Decode does not remove, rename, default, or coerce a key.

JSON object property order has no semantic meaning. Canonical encoding emits keys in the order shown in section 3.2.

The database stores `params` as `jsonb`. Exact object equality in the database constraint forbids missing and excess keys.

Database constraints are defense in depth. The domain decoder remains the authority for the complete cross-field union.

## 5. Scope and applicability

The rule scope union remains smaller than the general 0055.1 grant scope union:

```ts
type AuthzRuleScope =
  | { readonly _tag: "Global" }
  | { readonly _tag: "Domain"; readonly domainId: DomainId }
  | { readonly _tag: "Department"; readonly departmentId: DepartmentId };
```

For the capabilities in this amendment, the only legal domain ID is `receipts`.

The canonical domain scope is `Domain(DomainId("receipts"))`. There is no `Receipt` or `Tenant` variant.

The old `Receipt` decoder, alias, and write shape MUST NOT return.

A rule applies to one canonical receipt context only when all conditions are true:

1. The rule capability equals the evaluated capability.
2. The rule is active at the authorization instant.
3. The `Person` or active `Tag` subject matches the principal at that instant.
4. `Global` matches the receipt context.
5. `Domain(receipts)` matches `context.domainId` exactly.
6. `Department(D)` matches `context.departmentId` exactly.

A caller-supplied department is not a canonical context. A rule scope never replaces resource-context resolution.

The `receipts.by-id` resolver supplies one `ExactlyOne` context for an item or command:

```ts
type ReceiptRuleContext = CanonicalResourceContext<ReceiptAccessFacts> & {
  readonly domainId: typeof RECEIPT_DOMAIN_ID;
  readonly departmentId: DepartmentId;
  readonly resource: {
    readonly kind: "receipt";
    readonly id: ReceiptId;
  };
};
```

The registered context owns the receipt state and approver relationship facts. Request input cannot supply or override those facts.

## 6. Requirement composition laws

### 6.1 Compilation boundary

The rule compiler receives decoded rules, the resolved principal, one authorization instant, and one canonical context.

It produces typed evidence contributions, typed requirement contributions, and provenance. It does not receive precomputed requirement results.

The current `CapabilityRequirement.satisfied` model is removed. No compatibility type or adapter remains.

The current optional caller inputs `parameterFills` and `requirements` are removed from rule-compilation request facts.

Endpoint and grant requirements still enter through their 0055.1 owners. They do not enter as caller-authored Booleans.

### 6.2 Registry evaluation

For each applicable requirement rule, the compiler MUST perform these steps:

1. Decode the exact rule variant.
2. Map its payload to `TypedRequirement`.
3. Find the requirement in `REQUIREMENT_TYPES`.
4. Verify that the registration accepts `receipts.by-id`.
5. Verify the registration context schema against the resolved context.
6. Decode the empty parameters with the registered parameter schema.
7. Call the registered evaluator with the principal and that context.
8. Preserve the returned typed result and safe provenance.

The compiler MUST NOT call a function selected from operator data. It MUST NOT accept `satisfied` from a caller or row.

`receipts.pending` reads `context.facts.state`. It is satisfied only when that canonical value is `Pending`.

`receipts.approver-relationship` reads the canonical approver relationship. It is satisfied only when the principal is in that relationship.

Both evaluations use the same principal, context, authority version, and authorization instant as the capability decision.

A registry mismatch, invalid context, or invalid parameters fails closed. It cannot make the rule inert.

### 6.3 Canonicalization and duplicates

A canonical requirement key is the requirement ID plus the canonical encoding of its decoded parameters.

For the two accepted effects, the only keys are:

```text
receipts.pending + {}
receipts.approver-relationship + {}
```

Applicable rules are ordered by `ruleId`. Requirements are ordered by capability registry order, then by canonical parameter encoding.

Identical requirement contributions collapse to one evaluation. Their provenance retains every distinct source.

For rule contributions, provenance is the sorted unique, nonempty list of contributing `ruleId` values.

Reversing database row order, tag-assignment order, or caller iteration order MUST produce byte-identical canonical composition evidence.

A duplicate does not strengthen, weaken, or evaluate a requirement twice. Removing one duplicate leaves the requirement active while another source remains.

A requirement from a rule can duplicate an endpoint or grant requirement. Evaluation still occurs once, and provenance retains all source kinds.

Provenance is evaluation evidence. It is not a verdict, grant, session value, or new authority row.

### 6.4 Ambiguity

The 0056 ambiguity law remains global:

1. Identical fills for one parameter slot collapse.
2. Different fills for one parameter slot produce `Ambiguous` and deny.
3. Identical requirement ID and parameters collapse.
4. Conflicting parameters for one requirement ID produce `Ambiguous` and deny.

No legal rule in this amendment can produce parameter-fill ambiguity. There is no parameter-rule variant.

No legal requirement rule can produce conflicting parameters. Both registered parameter schemas accept only `{}`.

An unsupported persisted value fails decode before composition. It is not converted into an ambiguity result.

### 6.5 Decision law

Rule requirements are conjunctive with endpoint and used-grant requirements.

The final evaluator applies the 0055.1 order for each context:

1. Resolve and validate the principal.
2. Resolve the canonical context.
3. Compose active grants and delegate contributions.
4. Satisfy the required capability expression.
5. Verify time and scope.
6. Evaluate all canonical requirements through `REQUIREMENT_TYPES`.
7. Return `Allow` only when every term succeeds.

A missing capability remains a capability denial. A requirement-only rule cannot change it into an allow.

One failed rule requirement returns the access denial stage `Requirement` and reason `RequirementFailed`.

Detailed requirement IDs, registered reasons, and provenance remain safe internal evidence. They do not change HTTP semantics.

The contributing rule-ID list includes delegate rules and requirement rules that contributed to the evaluated result.

## 7. State and decision flow

```text
decoded request + resolved principal
                |
                v
capture one authorization instant
                |
                v
receipts.by-id resolves canonical receipt context
                |
                +--> missing or inconsistent context: fail closed
                v
read direct authority + applicable rule/tag rows
                |
                v
strictly decode every selected row
                |
                +--> unsupported row: fail the whole read
                v
compile delegate facts + typed requirements + provenance
                |
                +--> ambiguous contribution: Deny(Ambiguous)
                v
evaluate capability, scope, time, and REQUIREMENT_TYPES
                |
                +--> failed requirement: Deny(RequirementFailed)
                v
Allow(principal, canonical context, authorization instant)
                |
                +--> SnapshotRead: project from the same snapshot
                |
                +--> Transaction: transition and record owned effects
```

No stage reads an access verdict from a rule, tag, credential, route, or request field.

## 8. Per-receipt command and collection behavior

### 8.1 Approval commands

Every command that uses `approveReceipt` MUST resolve its target through `receipts.by-id`.

The command path performs these operations inside one transaction:

1. Decode the command and credential-owned principal input.
2. Capture the authorization instant.
3. Lock and read the target receipt and required parent state.
4. Build the canonical receipt context from those rows.
5. Lock and read applicable direct authority, rules, and tag assignments.
6. Compile delegate and requirement effects for that exact context.
7. Evaluate both accepted requirement types through `REQUIREMENT_TYPES`.
8. On `Allow`, run the domain transition and its owned effects.
9. On denial, roll back without a transition or success effect.

A denial performs no receipt transition, success audit record, outbox append, idempotency success write, or file effect.

The authorization path MUST NOT decide from `{ domainId, departmentId }` without the receipt resource and facts.

A concurrent receipt, rule, grant, or tag-assignment change has one database order with the command.

### 8.2 Approval collection projections

An approval collection uses one consistent read snapshot and one authorization instant.

The domain query resolves a canonical context for each candidate receipt in stable receipt order.

For each context, it independently performs scope, capability, and requirement evaluation. It includes only allowed contexts in the projection.

A global or department grant can define a safe candidate set. It cannot provide one final Boolean for the board.

A global or department rule can be applicable to many contexts. Its requirements still evaluate separately for each receipt.

A status query can narrow candidates. It cannot replace `receipts.pending` evaluation for each returned resource.

The implementation MUST NOT authorize a department and then return all receipts from that department without per-receipt evaluation.

The implementation MUST NOT evaluate one representative receipt, first row, or aggregate state.

If no context remains allowed, the existing 0055.1 `AllMatching` denial law applies. This amendment does not define a new HTTP result.

## 10. Persistence migration

The matching implementation adds `packages/database/migrations/0026-declarative-rule-reconciliation.sql`.

The migration changes no rule ID, subject, scope, interval, revision, or existing delegate payload.

It adds no verdict, Boolean requirement result, executable expression, or second rule table.

### 10.1 Mandatory preflight

Before it drops or replaces a rule constraint, the migration MUST inspect every row in `public.authz_rules`.

A row is supported only when its complete target semantic value decodes as one variant in section 3.2.

The preflight also verifies subject columns, canonical scope columns, interval order, and required references.

If one row is unsupported, the migration raises an error and aborts the complete transaction.

The error identifies each unsupported `rule_id` and a bounded reason. It MUST NOT include ciphertext or other secret parameter values.

The migration MUST NOT coerce, delete, ignore, quarantine, reinterpret, or partially update an unsupported row.

The migration MUST NOT map a Boolean `satisfied` value to a requirement.

The migration MUST NOT treat an unknown requirement as an inert rule.

### 10.2 Target constraints

The `effect_kind` check retains all three global values.

The capability-and-parameters check accepts exactly the five rows in section 3.2. Every other combination reaches `FALSE`.

For requirement effects, database `jsonb` equality uses these exact values:

```json
{"requirementId":"receipts.pending","parameters":{}}
```

```json
{"requirementId":"receipts.approver-relationship","parameters":{}}
```

The scope check retains only `Global`, `Domain(receipts)`, and `Department(D)` for the current rule capabilities.

The migration does not restore the old `Receipt` value. It performs no dual write.

Existing supported delegate rows remain semantically and byte-for-byte unchanged in their owned columns.

### 10.3 Write and read boundaries

Every writer, including disposable backfill and fixtures, decodes with the target `AuthzRuleSchema` before SQL execution.

A write failure occurs before persistence. The database constraint remains a second defense.

Every row loader decodes the database projection and then decodes the complete target rule union.

If one selected row is invalid, the complete authority read fails closed. The loader MUST NOT skip that row and continue.

A read error is an infrastructure or decode failure. It is not an authenticated denial and not an inert rule.

Production execution of this migration still requires separate operator authority.

## 13. Disposable tracer journey

## 14. Equivalence and exact falsifiers

This amendment inherits every applicable falsifier from 0055.1, 0056, and 0056.1.
