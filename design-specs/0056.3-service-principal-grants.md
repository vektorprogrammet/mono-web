# Design spec 0056.3 — service-principal grants

## Metadata

| Field | Value |
| --- | --- |
| Goal | Add one explicit, resource-bound service-principal authorization path without turning OAuth identity, client metadata, scope, or rules into implicit authority. |
| Status | Frozen before implementation. This document is the complete normative 0056.3 boundary. |
| Base | `f85ac403ee70b09510b9149409e9b6d32d3de051` |
| Depends on | Frozen 0055.1 principal, credential, and access algebra; 0056.2 declarative rule reconciliation; 0077.2 native resource operation matrix; 0082 native OAuth provider |

## 1. Scope and authority

This amendment authorizes one service-principal journey only:

```text
GET /api/receipt-approval-queue
operation ID receipts.listReceiptsForApproval
0077.2 external row 42
```

It does not authorize another service-enabled operation, operation family, capability, domain, department, collection, mutation, internal route, or compatibility route.

The service journey retains all 0055.1 decision terms. A service bearer authenticates one `ServicePrincipal`; it does not carry an access verdict. An explicit active resource grant is required for each receipt that can appear in the approval queue.

This amendment does not create a general service role or a broad service grant. It does not enable `OAuthServiceBearer` on any other `AccessSpec`.

The implementation is a clean cutover. It has no fake service user, synthetic `Person`, alias endpoint, old `/api/admin/receipts` fallback, temporary in-memory grant map, hard-coded client allow, or second access registry.

## 2. Live source and frozen resolutions

At the base revision:

1. `PrincipalSchema` and `OAuthCredentialAuthority` already resolve `OAuthServiceBearer` to `ServicePrincipal(ServicePrincipalId)`.
2. `public.service_principals` and `auth.oauth_client_bindings` already enforce the one-to-one Service client binding.
3. `auth."oauthClientResource"` binds a client to `urn:vektorprogrammet:native-api`.
4. A valid service token has a tracked `jti`, `sub = client_id`, no `sid`, and no refresh family.
5. No production `AccessSpec` accepts `OAuthServiceBearer`.
6. `AuthzRuleSubjectSchema` and `public.authz_rules` accept only `Person | Tag`.
7. `authzRuleSubjectApplies` and the PostgreSQL rule projection require a `PersonId`.
8. The generic 0055.1 `Grant` and access evaluator already accept a `ServicePrincipal` subject.
9. Receipt approval list evaluation is person-keyed and applies `receipts.pending` and `receipts.approver-relationship` per receipt.
10. The current HTTP route still uses `/api/admin/receipts`; frozen 0077.2 row 42 replaces it with `/api/receipt-approval-queue`.

The matching implementation resolves these mismatches in one change. It does not implement unrelated 0077.2 rows.

## 3. Explicit identity, client, protected-resource, operation, and domain-resource binding

One persisted service grant binds all of these identities:

```ts
type ServicePrincipalReceiptGrant = {
  readonly grantId: GrantId;
  readonly servicePrincipalId: ServicePrincipalId;
  readonly clientId: OAuthClientId;
  readonly protectedResource: "urn:vektorprogrammet:native-api";
  readonly operationId: "receipts.listReceiptsForApproval";
  readonly capability: "approveReceipt";
  readonly resource: {
    readonly kind: "receipt";
    readonly id: ReceiptId;
  };
  readonly startAt: AuthorizationInstant;
  readonly endAt: AuthorizationInstant | null;
  readonly revokedAt: AuthorizationInstant | null;
  readonly revision: Revision;
};
```

Every field is authority data. None is inferred from a route prefix, token scope, client kind, client name, service-principal name, OAuth subject, request query, membership, tag, or previous request.

A grant is valid only when all referenced rows agree:

1. `public.service_principals.service_principal_id` names the grant subject.
2. `auth.oauth_client_bindings` names the same principal and has `client_kind = Service`.
3. The bound provider client is live.
4. `auth."oauthClientResource"` links that client to the exact protected resource.
5. The domain resource is one existing receipt.
6. The operation, capability, resource kind, and protected-resource values equal the closed literals above.

The one-to-one client binding is immutable. Replacing a Service client requires a new service principal and new grants; a grant cannot be rebound.

The grant stores no client secret, bearer, `jti`, token hash, OAuth scope, person ID, membership, role, tag, or authorization result.

## 4. Closed grant semantics

A service grant is a candidate 0055.1 grant with this exact projection:

```ts
{
  grantId,
  subject: { _tag: "ServicePrincipal", servicePrincipalId },
  capability: { type: "approveReceipt" },
  scope: {
    _tag: "Resource",
    resource: { kind: "receipt", id: receiptId },
  },
  startAt,
  endAt,
  requirements: [],
  source: `service-principal-grant:${grantId}`,
  revision,
}
```

The persistence boundary accepts no `Global`, `Domain`, `Department`, `And`, or `Or` service grant. It accepts no other capability or operation. This is the meaning of “no broad grant” in this amendment.

A grant is active exactly when:

```text
startAt <= authorizationInstant
AND (endAt is null OR authorizationInstant < endAt)
AND revokedAt is null
```

Intervals are half-open. `endAt <= startAt` is invalid. Revocation is monotonic and immediate for the next authorization read.

Multiple active grants for the same service principal and receipt collapse by `grantId` order into one semantic capability contribution. Duplicates do not widen scope. Invalid or inconsistent rows fail the complete authority read; they do not become inert rows.

A live service principal, Service client, client/resource link, OAuth `native-api` scope, valid token, or matching client ID contributes zero grants by itself.

## 5. Rule subjects and rule limits

The rule-subject union becomes:

```ts
type AuthzRuleSubject =
  | { readonly _tag: "Person"; readonly personId: PersonId }
  | { readonly _tag: "Tag"; readonly tagId: AuthzTagId }
  | {
      readonly _tag: "ServicePrincipal";
      readonly servicePrincipalId: ServicePrincipalId;
    };
```

Applicability receives the resolved non-anonymous `Principal`, not a fallback `PersonId`.

The exact subject laws are:

1. A `Person` subject applies only to the same `Person` principal.
2. A `Tag` subject applies only to a `Person` with one active matching tag assignment.
3. A `ServicePrincipal` subject applies only to the same `ServicePrincipal` principal.
4. A tag never applies to a service principal.
5. A person rule never applies through a Service client, and a service rule never applies through a user bearer or cookie.
6. `CapabilityHolder` is not a legal rule subject.

Service-principal rules are deliberately non-granting. The strict decoder accepts a `ServicePrincipal` subject only for an `approveReceipt` `requirement` rule with `Resource(receipt, receiptId)` scope and one of the two existing exact parameters:

```json
{"requirementId":"receipts.pending","parameters":{}}
```

```json
{"requirementId":"receipts.approver-relationship","parameters":{}}
```

A ServicePrincipal delegate rule is rejected. A ServicePrincipal Global, Domain, Department, And, or Or rule is rejected. A service rule can add a conjunctive requirement to an already explicit matching grant; it cannot create the grant, widen its resource, or make a requirement pass.

Person and Tag rule shapes, delegate behavior, requirement behavior, interval laws, ordering, duplicate collapse, and provenance remain unchanged.

## 6. Exact row 42 access assignment

0077.2 external row 42 is amended to this exact `AccessSpec`:

```text
External;
[BetterAuthCookie, OAuthUserBearer, OAuthServiceBearer];
[Person, ServicePrincipal];
One(approveReceipt);
receipts.approval-queue;
[receipts.pending, receipts.approver-relationship];
Reveal;
SnapshotRead
```

No other 0077.2 row changes.

The operation keeps one colocated `AccessSpec`. There is no mechanism-specific route, duplicate operation, service path, or operation-to-access map.

Credential resolution remains exact:

- `BetterAuthCookie -> Person`;
- `OAuthUserBearer -> Person`;
- `OAuthServiceBearer -> ServicePrincipal`;
- cookie plus bearer, multiple bearers, wrong bearer kind, or any unaccepted combination is credential rejection;
- valid service credentials sent to any other operation remain `WrongMechanism` and produce 401.

## 7. Canonical receipt context and requirements

The approval-queue resolver returns `AllMatching` contexts in stable receipt order from one consistent snapshot and one authorization instant.

For a Person, existing direct authority, role/rule macros, membership-derived approver relationship, and per-receipt requirement semantics remain unchanged.

For a ServicePrincipal, the candidate set begins with receipts named by active, non-revoked exact service grants for the resolved principal/client/protected-resource/operation binding. The implementation never scans all receipts and applies a broad service grant.

`ReceiptAccessFacts` adds this bounded field:

```ts
readonly approverServicePrincipalIds: ReadonlyArray<ServicePrincipalId>;
```

For each candidate receipt, the adapter derives that field only from active exact grants that bind the same service principal, client, protected resource, operation, and receipt at the one authorization instant. Values are sorted and unique.

`receipts.approver-relationship` evaluates as follows:

- `Person`: the person is in `approverPersonIds`;
- `ServicePrincipal`: the principal is in `approverServicePrincipalIds`;
- every other principal kind: failed.

This does not infer a relationship from OAuth identity. The same explicit resource grant row warrants both the resource-scoped capability contribution and the service approver relationship for that exact receipt. It cannot warrant another receipt.

`receipts.pending` continues to read the canonical receipt state. A grant cannot bypass it.

Every candidate context independently evaluates capability, grant interval and revocation, resource scope, endpoint requirements, applicable rule requirements, and current receipt state. Zero allowed contexts is a typed authorization denial, not an empty success.

## 8. Current authorization, disablement, and revocation

Every request recalculates both credential state and domain authority. No service grant, operation ID, receipt ID, capability, requirement result, or verdict is copied into the JWT, token-state row, client binding, introspection response, process cache, or OAuth scope.

The next request observes these exact outcomes:

| Change | Credential outcome | Access outcome | HTTP projection |
| --- | --- | --- | ---: |
| Access-token `jti` revoked | Rejected `Revoked` | Not evaluated | 401 |
| Service principal disabled | Rejected `Revoked` | Not evaluated | 401 |
| Service client disabled, expired, or unbound | Rejected | Not evaluated | 401 |
| Client/resource link absent | Rejected `Invalid` | Not evaluated | 401 |
| Service grant revoked or ended | Accepted | Capability/resource context denied | 403 |
| Receipt no longer pending | Accepted | Requirement denied | 403 |
| Applicable service rule requirement fails | Accepted | Requirement denied | 403 |

Grant revocation does not revoke an otherwise valid bearer. Credential disablement does revoke bearer use. These are separate authorities and separate denial stages.

A SnapshotRead uses one consistent snapshot for credential state, service/client/resource binding, grants, applicable rules, receipt contexts, requirements, decision, and response projection.

## 9. Audit evidence

Grant lifecycle changes append to `public.service_principal_grant_audit`. The closed event kinds are:

- `service-principal-grant-created`;
- `service-principal-grant-ended`;
- `service-principal-grant-revoked`.

Each row contains:

- random `event_id` primary key;
- `occurred_at`;
- closed `event_kind`;
- `grant_id`;
- `service_principal_id`;
- `client_id`;
- exact protected resource;
- exact operation ID;
- exact capability ID;
- exact receipt ID;
- resulting revision;
- bounded operator actor;
- required request correlation.

The relation is append-only for the application role. Update and delete are rejected.

Successful and denied resource requests use the 0055.1 bounded access trace. They do not append one grant-audit row per read.

No audit, log, trace, metric, exception, assertion, fixture artifact, or test output may contain a bearer, client secret, token hash, raw Authorization header, OAuth request body, private key, or arbitrary unbounded caller text.

Safe trace evidence contains only registered IDs, the service-principal ID, client ID, protected-resource ID, receipt ID, `jti`, grant ID, rule IDs, requirement IDs, denial stage, status, revisions, and timestamps.

### 10.1 Service grants

`public.service_principal_grants` has these columns:

| Column | Contract |
| --- | --- |
| `grant_id` | Primary key; strict `GrantId` |
| `service_principal_id` | FK to `public.service_principals`, delete restricted |
| `client_id` | FK to `auth.oauth_client_bindings`, delete restricted |
| `protected_resource` | Exact `urn:vektorprogrammet:native-api` |
| `operation_id` | Exact `receipts.listReceiptsForApproval` |
| `capability_id` | Exact `approveReceipt` |
| `resource_kind` | Exact `receipt` |
| `resource_id` | FK to the canonical receipt identifier, delete restricted |
| `start_at` | `timestamptz` |
| `end_at` | Nullable `timestamptz`; greater than `start_at` |
| `revoked_at` | Nullable monotonic `timestamptz` |
| `revision` | Nonnegative integer |
| `created_at`, `updated_at` | Ordered `timestamptz` |

A composite FK or equivalent closed constraint requires the exact Service client/principal pair. Another composite FK requires the exact client/protected-resource link. Checks reject an unknown operation, capability, resource kind, empty ID, inconsistent interval, revocation before creation, or backwards update time.

The lock/read index is ordered by `service_principal_id`, `client_id`, `protected_resource`, `operation_id`, `resource_kind`, `resource_id`, `start_at`, and `grant_id`.

### 10.2 Rule subjects

Migration 0028 adds nullable `subject_service_principal_id`, `resource_kind`, and `resource_id` columns to `public.authz_rules`.

It replaces the subject, scope, and parameter checks atomically:

- Person and Tag rows preserve their exact existing shapes.
- ServicePrincipal rows require `subject_service_principal_id` and forbid person/tag subject IDs.
- Only ServicePrincipal rows can use Resource scope in this amendment.
- A ServicePrincipal row is accepted only for one of the two exact requirement variants in section 5.
- Every other ServicePrincipal capability/effect/scope/parameter combination is rejected.

The migration adds a ServicePrincipal rule lock-order index. It does not add service tag assignments.

### 10.3 Audit

Migration 0028 creates `public.service_principal_grant_audit` with the exact section 9 event and field checks, foreign keys with delete restriction, an ordered lookup index, and append-only enforcement.

### 10.4 Migration laws

The migration is sequential and repository-owned. Runtime auto-migration remains disabled.

It preserves every existing Person and Tag rule byte-for-byte. Existing grants, tags, tag assignments, OAuth clients, service principals, resource links, token state, and audit rows remain unchanged.

A migration preflight aborts before constraint replacement if an existing row cannot satisfy the retained Person/Tag target schema. An abort changes no row or constraint.

There is no compatibility subject, nullable binding fallback, dual grant table, data-dependent default grant, backfilled service authority, or production fixture row.

## 11. Domain and adapter boundary

The domain authorization package owns:

1. the strict `ServicePrincipalReceiptGrant` schema;
2. projection to the 0055.1 `Grant`;
3. active/revoked interval evaluation;
4. service rule-subject applicability;
5. stable duplicate and provenance ordering;
6. service approver-relationship requirement evaluation;
7. the pure per-context authority decision.

The database/OAuth adapter owns:

1. strict decode before every write;
2. fail-closed complete-row decode after every read;
3. current joins across service principal, immutable Service client binding, provider client, client/resource link, grant, rule, and receipt;
4. shared authorization lock ordering;
5. create, end, and revoke transactions with append-only audit;
6. stable candidate receipt contexts;
7. mapping OAuth credential evidence to the exact current client/resource binding without exposing credential bytes.

The adapter exposes an Effect Service and Layer. Portable domain code does not import `pg`, Better Auth, provider modules, ambient configuration, or a live runtime.

## 14. Disposable PostgreSQL tracer

The implementation adds one bounded tracer that starts only after explicit heavy-job authorization.

It uses disposable PostgreSQL, the real 0082 auth engine, the exact section 12 fixtures, the production external router, and the exact row 42 endpoint.

The service journey observes, in order:

1. provision one Service client and service principal;
2. request exactly `native-api` for `urn:vektorprogrammet:native-api`;
3. verify `OAuthServiceBearer -> ServicePrincipal` and a tracked `jti`;
4. call `GET /api/receipt-approval-queue` with no grant and observe 403;
5. create the one exact resource grant and call again with the same bearer;
6. observe only `service-receipt-approval-pending` and 200;
7. verify the nonpending and foreign receipts are absent;
8. revoke the grant and call again with the same still-valid bearer;
9. observe credential acceptance followed by 403;
10. disable the service principal and call again;
11. observe credential rejection and 401;
12. inspect only bounded audit and access evidence;
13. clean every proof-owned row, process, and connection.

The delegated browser tracer also uses the exact row 42 endpoint named in section 12. Its direct grant removal still changes a valid user bearer from 200 to 403. The service implementation cannot replace, weaken, or redirect that journey.

No tracer uses a production hostname, production credential, shared database, provider account, remote service, fake service user, or retained secret.

## 15. Exact falsifiers

This amendment is not implemented if any condition below occurs:

1. A service principal is represented by `auth.user`, `Person`, membership, role, or tag.
2. A Service client, client ID, client kind, OAuth scope, resource link, token, or valid signature creates a grant.
3. A grant omits or infers its service principal, client, protected resource, operation, capability, or receipt.
4. A service grant uses Global, Domain, Department, And, Or, wildcard, query-selected, or route-derived scope.
5. A service grant enables any operation other than `receipts.listReceiptsForApproval`.
6. Any other `AccessSpec` accepts `OAuthServiceBearer`.
7. Row 42 loses either Person credential journey or either existing endpoint requirement.
8. A service grant bypasses `receipts.pending` or per-receipt evaluation.
9. One resource grant exposes a different receipt.
10. A service rule delegates authority, uses a broad scope, or applies without an explicit matching grant.
11. A Tag subject applies to a service principal.
12. A Person subject applies through a service credential or a ServicePrincipal subject applies through a person credential.
13. An unknown or inconsistent persisted row becomes inert instead of failing the authority read.
14. Grant or rule ordering changes the decision or evidence.
15. A grant or rule is active at `endAt`.
16. Grant revocation makes a still-valid bearer return 401 instead of current authorization denial 403.
17. Service-principal, client, or token revocation returns 403 instead of credential rejection 401.
18. A bearer stores or caches a current grant, receipt, operation, capability, requirement result, or verdict.
19. A SnapshotRead mixes credential, binding, grant, rule, receipt, or response facts from different snapshots.
20. The external service journey uses `/api/admin/receipts`, an alias, redirect, proof route, direct handler, or duplicate access registry.
21. The delegated browser tracer uses any endpoint other than `GET /api/receipt-approval-queue` with operation ID `receipts.listReceiptsForApproval`.
22. A fixture creates a fake service person, browser session, consent, refresh token, membership, role, or tag.
23. A client secret, bearer, token hash, Authorization header, or private key appears in evidence.
24. Migration 0028 backfills a service grant or weakens an existing Person/Tag constraint.
25. Runtime boot mutates schema.
26. A compatibility decoder, alias, temporary map, dual table, fallback principal, hard-coded client allow, or alternate service operation remains.

## 17. Explicit deferrals

This amendment defers:

- every other service-enabled native operation;
- broad, department, domain, global, composite, wildcard, role-derived, or tag-derived service authority;
- service-principal browser sessions, consent, refresh tokens, memberships, roles, and tags;
- dynamic OAuth client registration or additional protected resources, audiences, or scopes;
- service-principal mutation endpoints or public grant administration APIs;
- production client, grant, key, credential, database, provider, ingress, or deployment effects;
- unrelated 0077.2 route, OpenAPI, dashboard, SDK, generated documentation, and release cutovers.
