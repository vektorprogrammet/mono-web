# Design spec 0078.1 — claim-specific parity evidence amendment

> **Summary:** Move the composed capability comparator's four tracer rows from `unknown` to warranted verdicts by producing real, claim-specific runtime evidence. Each evidence claim is OBSERVED through a disposable per-backend journey that drives the real HTTP API of one backend, never asserted by static inspection. The external intent and evidence authorities remain read-only; v2 accepted-intent and runtime-evidence registers are committed in-repo under `evidence/capability-parity/` with pinned digests, explicit provenance, and a verification receipt.

## Scope

## Claim kinds the comparator already requires

The comparator (`packages/parity-inventory/src/capability-parity.ts`) requires these claim kinds from `functional-parity-capability-runtime-evidence/v2` receipts. The amendment observes each one, it never asserts it:

| Claim kind | Required when | Observation method |
|---|---|---|
| `operation_observed` | every witness operation node | The journey issues the exact HTTP operation (`method` + path template + status recorded with request/response digests) against the backend's real listener. |
| `authorization_observed` | every `required_preconditions` entry | The journey sends the same request without a session (or with a session whose persona lacks the required grant) and observes the typed 401/403 boundary response. |
| `rejection_observed` | every `rejections` entry | The journey issues an invalid transition (e.g. duplicate application, stale-revision schedule, double-responded invitation) and observes the typed 409/422 response plus a state read-back proving `must_not_change_state`. |
| `persistence_observed` | every `side_effects` entry with `required_claim: "persisted_outbox"` | The journey reads the outbox/audit rows through a fresh DB read-back after the command and digests the read-back bytes. |
| `boundary_observation` | every `warranted_outcomes` entry | The journey reads the user-visible surface (response body or fresh authenticated read) and digests the observed value against `expected_json`. |
| `effect_requested` | every `side_effects` entry with `required_claim: "requested"` | The journey observes the ordered durable outbox request row that requests the provider effect (activation message, subscription, audit) after commit, with a fresh DB read-back. |
| `fresh_read_observed` | every `freshness` entry | The journey issues a second, later read through a new request after the write and digests the fresh observation. |
| `journey_executed` | every executed journey | The runner's bounded exit status; recorded but never sufficient for any semantic item. |

A receipt lacking a named observation method fails review. A claim without a backend witness fails `claimIsInWitnessScope` and is discarded with `CLAIM_SCOPE_INVALID`.

## Backend witness environments

### Native backend (Effect + disposable PostgreSQL)

The native witness run reuses the established runner pattern from `apps/dashboard/e2e/run-real-native-recruitment-assignment.mjs`:

1. `initdb` + `pg_ctl start` a disposable PostgreSQL cluster under a fresh `/tmp` root, loopback only, trust auth, destroyed after the run.
2. The canonical migrations run through the same `DatabaseLive` layer every capability uses.
3. A deterministic fixture seed ( personas, departments, periods, applications, interviews) is inserted; the seed bytes are the `fixture_digest` input.
4. The real backend starts via `bun run --cwd apps/backend start` against the disposable URL; readiness is observed through `GET /health`.
5. The runner drives `http://127.0.0.1:$BACKEND_PORT` directly over fetch — no browser. Persona sessions come from `POST /api/auth/sign-in/email` (the only permitted sign-in surface) and the returned `better-auth.session_token` cookie is forwarded on protected calls. Invitation-response calls carry `X-Recruitment-Invitation-Capability` from the observed scheduled interview's outbox/requested-capability material.
6. Every request, response status, sanitized response body, and DB read-back row is digested; no cookie value, password, or PII is stored.

### Legacy backend (Symfony PHP + disposable SQLite/loopback PHP server)

The legacy witness run reuses the established runner pattern from `apps/dashboard/e2e/run-real-symfony-core-journeys.mjs`:

1. The legacy checkout is the `mono-web` line at `bebab18258da5a0f993dfcc6f09ea5e8af7bf68e` (an ancestor of the frozen base revision, so the server sources match the pinned revision family).
2. PHP is the immutable Nix store `php-with-extensions-*` binary; a loopback `php -S` server serves the real `public/index.php` front controller; `APP_ENV=e2e`.
3. The database is a disposable SQLite file inside a fresh `/tmp` root created by `doctrine:schema:create`, seeded through `doctrine:fixtures:load` with a deterministic fixture group; the fixture bytes are the `fixture_digest` input.
4. Providers are disabled exactly like the established runner (`MAILER_DSN=null://null`, `SLACK_DISABLED=true`, `SMS_DISABLE=true`, disabled Google/Gateway tokens); every effect request is observed through persisted outbox/audit rows or recorded no-op delivery, never through a provider call.
5. The runner drives `http://127.0.0.1:8000` over fetch with the same claim-observation discipline as the native side.

### Legacy precondition gate

The legacy witnesses run only when the established disposable-PHP collector path works locally: the immutable Nix `php-with-extensions-*` binary boots `bin/console` against a disposable database and the `doctrine:schema:create` + fixture-load sequence succeeds. If this gate fails, the amendment records the exact reason and emits legacy rows as **observed-absent** (`MISSING_CLAIM_SPECIFIC_EVIDENCE` with `evidence_status: "missing"`), never fabricated. Observed-absent is not asserted absence: the report keeps `unknown`, and the diagnostics name why no legacy receipt exists.

## In-repo v2 registers (external authorities stay read-only)

The v1 authorities pin the external clean checkouts. This amendment commits the v2 registers inside the mono repository:

- `evidence/capability-parity/accepted-intent-v2.json` — the accepted-intent v2 register holding the four tracer intents with full semantic items and both-backend implementation witnesses;
- `evidence/capability-parity/capability-runtime-evidence-v2.json` — the capability runtime evidence v2 register holding one receipt per (backend, intent) executed journey.

Provenance rules:

- Both registers are canonical JSON (recursive key sort, compact UTF-8, no terminal newline), validated with the existing 0078 JSON Schemas before commit.
- Each register records its `source_authority` as an explicit pin of the EXTERNAL v1 authority (repository ref, path, revision, blob oid, byte digest, schema version) — the external files are inputs and stay untouched.
- The evidence register's `source_authority` additionally pins the in-repo accepted-intent v2 register (same pin shape, `repository_ref: "in-repo:evidence/capability-parity"`).
- Receipts record `backend_revision_ref`, `openapi_sha256`, `operation_sha256`, `implementation_digest`, `runner_digest`, and `fixture_digest`; a receipt whose digests drift from the current catalogs/implementation is stale by construction and the verifier fails closed on it.

## Candidate migration intent

The `--migration-candidate` output of `capability-parity:verify` remains the deterministic v1→v2 migration candidate for the unreviewed remainder of the v1 register. The amendment does not hand-author that candidate; the committed in-repo register covers only the four tracer intents. The verifier continues to accept a v1 external register and pick the committed v2 intent register when present.

## Falsifiers

The check fails when any of these hold:

1. **Unnamed observation method** — a committed receipt whose runner or fixture digest cannot be traced to an executed disposable run; or a claim whose kind has no named observation method in this amendment's claim-kind table.
2. **Claim without a backend witness** — a claim referencing a `witness_id`/identifier outside its backend's implementation witness; the comparator must discard it with `CLAIM_SCOPE_INVALID` instead of crediting it.
3. **Stale or undigested evidence** — a receipt with `result: "failed"`, nonzero exit, or provenance digests that do not match the current catalogs, source revision, or implementation digest; the comparator must report `RECEIPT_STALE`, never silently drop the row.
4. **Inferred (not observed) claim** — any claim derived from a route declaration, security scheme, status-code table, OpenAPI extension, or fixture expectation without a recorded observation against the running backend; assertions are authority, observations are receipts, and this amendment never converts the former into the latter.
5. **Authority mutation** — any byte change, mtime-touch semantic commit, or write attempt against `/srv/share/projects/vektorprogrammet/functional-parity-{intent-authority,runtime-evidence}` invalidates the run; the external registers must remain byte-identical before and after.

The falsifier suite in `packages/parity-inventory/tests/` gains cases for scope rejection, stale provenance, and missing-claim diagnostics driven by journey-shaped fixtures.

## Deterministic report

After the v2 registers are committed, `bun run capability-parity:verify --mode check` must pass byte-deterministically:

- rows with both-backend warrantable claims resolve to `equivalent` or `not_equivalent` with named evidence;
- rows with native-only evidence resolve to `unknown` with the named missing legacy claim kinds;
- the applicant-assignment negative control stays `unknown` with `RECEIPT_STALE`;
- whatever verdict the comparator computes is the result — no upgrading, no suppression.

## Addendum (0078.2): collector executable allowlist gap

During the legacy witness lane it was established that the bwrap sandbox binary
was never actually missing on the build machine: `/etc/profiles/per-user/nori/bin/bwrap`
exists and works. The gate in `packages/parity-inventory/src/api.ts`
(`collectorExecutableProvenance`) only accepts `/usr/bin/bwrap` or a
`/nix/store/*-bubblewrap-*/bin/bwrap` path, so the user-profile install is
invisible to the collector. The same applies to php via
`resolveCollectorExecutablesWithServices`. Recorded here as a known allowlist
gap; intentionally NOT fixed in api.ts, whose bytes are pinned by
`native-run-manifest.json` (`CLAIM_EVIDENCE_RUNNER_DRIFT`). The legacy witness
lane therefore validates its php executable directly through
`validateCollectorExecutablePathWithServices` with the Nix store path.
