## 1. Amendment authority

This amendment corrects the release count in design spec 0079.2.
It replaces each 52-operation release requirement with 57 public external operations.
The one internal operation stays separate.

Design specs 0079, 0079.1, and 0079.2 remain active where they are compatible with this amendment.
This amendment has authority over conflicting release-count requirements in design spec 0079.2.

## 2. Canonical release scope

`ExternalNativeApi` contains the 52 operations from design spec 0077.2 and the five operations from design spec 0077.3.
Thus, `ExternalNativeApi` contains 57 public external operations.

`InternalNativeApi` contains the existing receipt-evidence operation.
It contains no operation from design spec 0077.3.
The complete server projection contains 58 operations.

Design spec 0077.3 section 5 is the canonical source for the five added methods, paths, operation IDs, schemas, effects, and access values.
This amendment does not copy that route table.
No generator reads this amendment as a route registry.

## 3. Corrected release artifacts

### 3.1 Public OpenAPI

`packages/http-api/openapi.json` contains 57 unique public operation IDs.
It includes all five operations from design spec 0077.3 section 5.
Each public operation has one reflected `x-vektor-access` value.

The document keeps OpenAPI version 3.1.0 and release version `0.2.0`.
It excludes the internal operation and all Better Auth `/api/auth/*` routes.

### 3.2 Generated SDK

`packages/sdk/native-api-operations.json` contains 57 operations.
The generated Effect client exposes the five methods from design spec 0077.3.
Their request and response types come from `ExternalNativeApi` reflection.

The Promise client remains a mechanical adapter over the Effect client.
It does not own a route list, schema, response mapping, or access rule.
The SDK package version stays `0.2.0`.

### 3.3 Server metadata

`apps/backend/src/generated/native-api-metadata.json` contains 57 external operations and one internal operation.
It contains 58 unique operation IDs.
The five added entries include their reflected runtime access values.

The internal operation keeps its separate ingress and `internal` visibility.
No metadata projection changes it into a public operation.

### 3.4 Documentation

The generated Vocs landing states that the public API contains 57 operations.
It also states that one internal operation is outside the public reference.
The landing keeps the `0.2.0` release and artifact provenance.

The public API pages include the five operations through the OpenAPI document.
No Markdown file contains a copied route inventory.
The generated code reference includes the new public contract from source comments.

### 3.5 Release manifest

`packages/http-api/release-manifest.json` records 57 external operations, one internal operation, and 58 total operations.
It records new SHA-256 digests for each changed generated artifact.
It keeps release version `0.2.0`.

The manifest records design specs 0077.3 and 0079.3 in its governing provenance.
It keeps the artifact paths and deterministic inputs from design spec 0079.2.

## 4. Password-recovery boundary

Design spec 0054.2 remains the authority for password recovery.
Password recovery stays under Better Auth `/api/auth/*`.
It does not enter `ExternalNativeApi` or `InternalNativeApi`.

Password recovery receives no native operation ID, `AccessSpec`, OpenAPI operation, or generated SDK operation.
It does not change the 57 external plus one internal release count.
The release projection does not restore the removed `client.auth` namespace.

## 5. Deterministic derivation and stale-artifact rejection

The release generator reflects `ExternalNativeApi` and `InternalNativeApi` directly.
It does not use a copied route table, count constant, SDK method list, or documentation inventory.

Stable sorting, final newlines, and SHA-256 rules remain as specified in design spec 0079.2.
Check mode generates candidates without changing tracked files.
It compares the exact candidate bytes with every owned artifact.

After the five source operations land, the previous 52-operation artifacts are stale.
Before regeneration, check mode must reject the stale OpenAPI, SDK inventory, server metadata, documentation, and manifest.
A stale artifact cannot pass because its old digest still matches another stale artifact.

After regeneration, two runs from unchanged sources produce identical bytes.
The new manifest hashes the final bytes of each listed artifact.
No old 52-operation digest remains authoritative.

## 6. Caller and browser falsifiers

The caller cutover and scan requirements in design spec 0079.2 remain active.
The caller disposition in design spec 0077.3 section 8 adds five required generated calls.
It does not restore `client.me`, `client.public`, or `client.admin`.

The scan rejects all five removed calls from design spec 0077.3.
It also rejects old route forms, old payload fields, legacy envelopes, and unmarked Symfony exceptions from design spec 0079.2.
Real and native modes return no fixture data after a failed read.

The profile read-and-update browser journey from design spec 0079.2 remains a release check.
The nine browser observations in design spec 0077.3 section 10.1 are additional release checks.
Neither set replaces or weakens the other set.

Browser network evidence contains no removed native route.
It also contains no Symfony origin or legacy API request during the five read journeys.
