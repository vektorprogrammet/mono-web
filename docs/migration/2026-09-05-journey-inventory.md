## Release implications

1. Stabilize the chosen revision and repair contact, with evidence from the committed artifact.
2. Complete a receipt cutover contract: scope/refund semantics, authoritative data and files, identity/permission mapping, reconciliation, observed effects, legacy write ownership and rollback. Existing import code should be evaluated before building another importer.
3. Treat tutor-to-school allocation and substitutes as operational migration gaps; extract complete semester journeys before implementation.
4. Give events, surveys, certificates and statistics explicit delivery or operator-approved retirement decisions. Absence from the native API is not authorization to retire them.
5. Resolve the actual wider economy workflow with the operator; do not equate receipt management with all financial work.

This document is a dated assessment, not a replacement migration registry. Future assessments should reference the executable contract and regenerated evidence at their own revision.
