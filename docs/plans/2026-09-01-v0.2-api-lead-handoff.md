## 5. Current v0.1 baseline

### 5.1 Contract authority

`packages/http-api/src/api.ts` defines `NativeApi`. This source is the authority for the native HTTP resource contract.

`packages/http-api/openapi.json` is a generated projection. The SDK and docs are consumers, not independent contract authorities.

The current SDK is mostly handwritten. It contains routes that are not in `NativeApi`.

### 5.2 Current public surface

The generated OpenAPI document uses OpenAPI 3.1 and version `0.1.0`. It contains 47 external operations.

The current source also contains one OpenAPI-hidden receipt evidence operation. The backend mounts that operation on the same external router.

The public paths still contain these v0.1 forms:

- `/api/admin/*`
- `/api/me`
- `/api/me/session`
- `/api/field_of_studies`
- slash-based actions such as `/submit`, `/revise`, and `/withdraw`

The current profile and session routes are not the final v0.2 routes. The current receipt approval list reuses the owner list projection.

### 5.3 Current authority model

Specifications 0054, 0055, and 0056 provide a strong base.

Identity resolves only a `PersonId`. Domain authorities resolve request facts at one authorization instant.

Declarative rules add typed evidence, parameters, or requirements. They do not store authorization verdicts.

The current capability registry is not exhaustive. It covers `approveReceipt`, `submitReceipt`, and `reviewApplicants` only.

### 5.4 Current command model

Many public mutations accept a body or multipart `commandId`. Several commands also accept a body revision.

The receipt domain stores command receipts, audit rows, and outbox rows. It detects a reused command ID with a changed request digest.

Current HTTP replay is not exact. Some first responses use 201, while their replays use 200 and add a `replayed` field.

### 5.5 Current package versions

The HTTP API and backend packages report version `0.1.0`. The OpenAPI document and native docs also report `0.1.0`.

The SDK package manifest reports `0.2.0`, but the published npm package did not use that version on 2026-09-01.

The SDK changelog stops at `0.1.2`. No pending changeset described the synchronized v0.2 release at the audit point.

## 6. Frozen v0.2 decisions

### 6.1 Resource grammar

1. Use strict lower-kebab plural nouns for collection resources.
2. Enumerate singleton exceptions. The known exceptions are `/health`, `/api/profile`, and `/api/session`.
3. Remove `/admin` and `/me` from paths, operation groups, SDK names, docs, tests, and examples.
4. Use standard resource methods for ordinary reads and writes.
5. Use PATCH for ordinary partial edits.
6. Use PUT only for complete replacement.
7. Use `:lower-kebab-action` for a custom transition.
8. Do not add v0.1 aliases, redirects, or compatibility routes in the preview cutover.
9. Do not infer administration authority from a path prefix.

### 6.2 Fixed resource names

Use these paths in the final matrix:

| Purpose                                | Final path and method                                           |
| -------------------------------------- | --------------------------------------------------------------- |
| Read profile                           | `GET /api/profile`                                              |
| Edit profile                           | `PATCH /api/profile`                                            |
| Read current session                   | `GET /api/session`                                              |
| End current session                    | `DELETE /api/session`                                           |
| List sessions                          | `GET /api/sessions`                                             |
| Revoke one session                     | `DELETE /api/sessions/{sessionId}`                              |
| Revoke other sessions                  | `POST /api/sessions:revoke-others`                              |
| Revoke all sessions                    | `POST /api/sessions:revoke-all`                                 |
| Read people directory                  | `GET /api/people`                                               |
| Read receipt approval work             | `GET /api/receipt-approval-queue`                               |
| Create an interview for an application | `POST /api/recruitment/applications/{applicationId}/interviews` |

The session collection returns session identifiers and device metadata. It never returns a reusable session token.

The receipt approval queue uses a distinct projection. It does not reuse the receipt-owner response by default.

### 6.3 Actions

Use colon actions only for transitions that do not fit a standard resource method.

Examples include these routes:

- `POST /api/receipts/{receiptId}:withdraw`
- `POST /api/receipts/{receiptId}:refund`
- `POST /api/receipts/{receiptId}:reject`
- `POST /api/recruitment/interviews/{interviewId}:schedule`
- `POST /api/recruitment/interviews/{interviewId}:finalize`
- `POST /api/recruitment/interviews/{interviewId}:cancel`
- `POST /api/recruitment/invitation-response:confirm`
- `POST /api/recruitment/invitation-response:reject`
- `POST /api/recruitment/invitation-response:request-new-time`
- `POST /api/content/articles/{articleId}:publish`
- `POST /api/content/articles/{articleId}:unpublish`

Do not create generic `/commands` or `/rpc` endpoints.

### 6.4 Idempotency

All external state-changing requests use the `Idempotency-Key` header. Public schemas do not expose `commandId`.

The HTTP adapter maps the header to an internal command ID. The domain keeps its command receipts, audits, and outbox records.

The idempotency identity includes these values:

- the authenticated principal or capability
- the qualified operation ID
- the normalized target resource
- the idempotency key
- the canonical semantic request digest

The idempotency key does not grant authority. Every replay resolves current authentication and authorization before it reads the stored response.

The same identity and digest return the exact first HTTP result. This result includes the status, body, media type, `Location`, `ETag`, and relevant headers.

The same identity with a different digest returns a 409 Problem Details response. An in-flight duplicate returns a retryable 409 with `Retry-After`.

The state change, idempotency receipt, audit row, and outbox row commit in one transaction.

### 6.5 Optimistic concurrency

Use strong opaque ETags for mutable item representations. Do not use a public integer revision as the primary HTTP precondition.

An existing-resource mutation requires `If-Match`. A missing header returns 428, and a stale ETag returns 412.

A business lifecycle conflict remains 409. An ETag is not an authorization token or an idempotency key.

Add item representations before a mutation depends on their ETags. This requirement applies to profile, receipts, admission periods, interviews, articles, and invitation responses.

### 6.6 Status and response headers

Use these defaults:

| Result                                      | HTTP response                                          |
| ------------------------------------------- | ------------------------------------------------------ |
| Successful read                             | 200, or 304 after a valid conditional read             |
| Resource creation                           | 201 with `Location`, representation, and strong `ETag` |
| PATCH or transition with an observation     | 200 with the observation and strong `ETag`             |
| Successful operation with no representation | 204                                                    |
| Exact idempotent replay                     | The exact first status and relevant headers            |

Do not use 202 only because an outbox effect remains pending.

### 6.7 Cache and CORS

Authenticated, session, service, and object-capability responses use `private, no-store` or `no-store`.

Mutation responses and error responses use `no-store`. Anonymous projections can use explicit public freshness and conditional reads.

Do not mix anonymous and authenticated representations on one cache-varying route. This rule controls the open admission-period decision.

Centralize CORS policy. Credentialed requests use an explicit trusted-origin list and never use `Access-Control-Allow-Origin: *`.

Allow the headers that the contract needs. These headers include `Authorization`, `Idempotency-Key`, `If-Match`, and `If-None-Match`.

Expose `ETag` and `Location`. Keep preflight behavior identical for all native groups.

### 6.8 Problem Details

Use RFC 9457 `application/problem+json`. Do not use the current `{error:{tag}}` envelope.

Each problem contains these stable fields:

- `type`
- `title`
- `status`
- a machine-readable `code`
- a safe `detail`
- optional `instance`
- typed validation details for applicable errors

Use endpoint-specific error unions. Do not expose a full domain error family on each endpoint.

Use these status classes:

- 400 for malformed requests and headers
- 401 for an absent or invalid credential, with `WWW-Authenticate`
- 403 for an authenticated principal without authority
- 404 for absence or an explicit concealment rule
- 405 with `Allow`
- 409 for business and idempotency conflicts
- 412 for a stale `If-Match`
- 413 for a payload that is too large
- 415 for an unsupported media type
- 422 for decoded domain validation
- 428 for a missing `If-Match`
- 429 with `Retry-After`
- 500 for an unexpected defect
- 503 for a known dependency outage

### 6.9 Access algebra

Separate the principal from the credential.

Use these principal variants:

```text
Anonymous
Person(PersonId)
ServicePrincipal(ServicePrincipalId)
CapabilityHolder(CapabilityId)
```

Use these credential mechanisms:

```text
None
BetterAuthCookie
OAuthUserBearer
OAuthServiceBearer
ObjectCapability<K>
```

A `Person` can authenticate with a first-party Better Auth cookie or a delegated OAuth bearer.

A `ServicePrincipal` uses an OAuth service bearer. A `CapabilityHolder` uses a typed object capability.

`Anonymous` uses no credential. A credential resolves a principal but does not contain the authorization verdict.

Every operation has an explicit exposure:

```text
External
Internal
```

Do not use a public path named `internal` as a security boundary. Use a separately constructed router or listener for internal operations.

### 6.10 Capabilities, grants, and scopes

Capabilities are closed branded identifiers. Unknown capabilities fail during decode or registration.

Permission bundles and roles are typed grants or grant-authoring macros. They never produce an authorization verdict by themselves.

A role never erases ownership, relationship, time, state, scope, or transaction requirements.

Use this scope algebra:

```text
Global
Domain(DomainId)
Department(DepartmentId)
Resource(ResourceKind, ResourceId)
And(Scope, Scope)
Or(Scope, Scope)
```

There is no `Tenant` type. Domain and Department are separate axes.

A resource resolves to its canonical domain and department contexts. Client input can narrow scope but cannot create it.

Global is the top scope. It is not a wildcard capability.

### 6.11 Decision time

Read operations use one consistent snapshot. Commands decide authority inside the state-change transaction.

A command resolves these items at one authorization instant:

1. the principal
2. the canonical resource context
3. current grants and rules
4. typed requirements
5. the resource lock and version
6. the decision
7. the state transition
8. the idempotency receipt
9. the audit row
10. the outbox row

A retry recalculates authority. It does not reuse the failed transaction facts.

### 6.12 OpenAPI access metadata

The vendor extension is `x-vektor-access`.

Every native operation has exactly one exhaustive `AccessSpec` beside its endpoint declaration. The generator emits the same data into OpenAPI.

Each `AccessSpec` contains these fields:

- exposure
- accepted credential mechanisms
- principal kind
- typed capabilities and requirements
- canonical scope resolver
- concealment policy
- decision time, `SnapshotRead` or `Transaction`

OpenAPI `security` describes credentials only. It does not replace `x-vektor-access`.

A generation gate rejects these conditions:

- a public operation without one `AccessSpec`
- an unknown capability or scope resolver
- an external `/admin` or `/me` path
- a Better Auth or internal route in the native resource document
- an SDK operation without a native operation ID

### 6.13 First-party sessions

Better Auth 1.7.1 cookies are for first-party browser sessions only.

Complete session hardening before OAuth work:

1. Disable public sign-up.
2. Disable the five-minute cookie cache for authoritative API session resolution.
3. Implement the exact session lifecycle in section 6.2.
4. Freeze CSRF rules and trusted origins.
5. Freeze secure cookie properties.
6. Remove residual environment token maps.
7. Add an append-only security audit.
8. Make revocation authoritative immediately.

A normal role cannot mint another person's session. Account provisioning does not issue a normal user session.

### 6.14 External OAuth

Pin `@better-auth/oauth-provider` at version `1.7.1`. Keep it version-matched with Better Auth 1.7.1.

Use the provider for OAuth protocol mechanics. Do not use the Better Auth bearer or JWT plugins as a substitute.

Use authorization code with S256 PKCE for delegated people. Require exact redirects, explicit consent, resource audience, and bounded scopes.

Use `client_credentials` for explicit service principals. Do not represent a service as a fake person.

Use opaque short-lived access tokens. Use rotating refresh-token families for delegated people.

Provide token revocation and authenticated introspection. Recalculate current domain authority for each resource request.

Defer personal access tokens, standalone API keys, device flow, and impersonation. Defer OIDC unless a named client requires it.

### 6.15 Release and version lifecycle

Release OpenAPI, the generated SDK operation layer, server metadata, and docs as one synchronized version `0.2.0`.

Create one release manifest from one immutable source commit. Put the SHA-256 digest of the exact canonical OpenAPI bytes in that manifest.

Embed or reference the same release version and digest in the SDK, server, and docs. Avoid a self-referential digest inside the OpenAPI bytes.

The v0.2 preview cutover removes all v0.1 aliases. First-party consumers move in the same cutover.

A future stable API uses `/api/v1`. A later major version uses RFC 9745 `Deprecation` and RFC 8594 `Sunset` headers.

Use the `Link` deprecation relation with those headers. Add a sunset date only after the operator approves a retirement commitment.

## 13. Worktree runbook

### 13.1 Start a work slice

1. Read this handoff.
2. Make sure that canonical still points to the recorded source line or an authorized successor.
3. Record the canonical full HEAD and clean status.
4. Create one branch and one worktree for one numbered specification.
5. Assign one writer to that worktree.
6. State the owned paths before the first edit.

### 13.2 Work in the slice

1. Keep feature commits coherent and small.
2. Stage files by explicit pathspec.
3. Do not use broad `git add -A`.
4. Do not reset, clean, or delete work that belongs to another writer.
5. Do not add aliases to make a partial cutover appear complete.
6. Keep source authority ahead of generated projections.
7. Record the exact command and scope for each check.

### 13.3 Integrate the slice

1. Stop the feature writer before integration.
2. Make sure that the canonical worktree is clean.
3. Apply the coherent commits to the dedicated integration branch.
4. Resolve contract conflicts at source, not in generated files.

7. Run the bounded checks before a root gate.
8. Keep the branch local until the operator approves a push.

### 13.4 Preserve worktrees

Do not prune historical worktrees without operator authority. Many old worktrees contain useful evidence or unmerged work.

Treat `/tmp` worktrees as temporary operational state. Commit durable decisions before the worktree disappears.

## 14. OOM runbook

Prior work lost time because concurrent heavy lanes triggered `systemd-oomd`. The machine can kill concurrent work.

Use this order:

1. Stop unused development servers and browser processes.
2. Run one package-focused check.
3. Run one generator check.
4. Run one bounded runtime witness.
5. Stop its database and service processes.
6. Run one root type check.
7. Run one root lint check.
8. Run one root build.
9. If its scope is necessary, run one root test lane.

Do not run root build, type, lint, and test lanes concurrently. Do not run multiple Vite, Playwright, PostgreSQL, or PHP evidence stacks together.

Use one browser worker for a heavy journey. Use one disposable database cluster at a time.

If memory pressure increases, stop the current lane before the next lane starts. Do not add retries to hide an OOM failure.

## 15. Operator boundaries

The following actions require explicit operator authority:

- push a branch or create a pull request
- publish a package or release
- deploy preview, docs, or production services
- change Cloudflare, DNS, routes, or worker bindings
- register an OAuth provider, client, redirect, or consent screen
- create, rotate, read, or write credentials and secrets
- change a shared or production database
- run a production migration or data import
- restart a shared or production service
- send external notifications
- remove material worktrees, branches, evidence, or user data

Local source edits and local bounded checks do not grant authority for these effects.

Prepare a separate authority capsule for each external action. Include the target, exact effect, rollback, evidence, and stop condition.

## 18. General lessons

1. Keep one executable contract authority. Generate OpenAPI, SDK operations, server metadata, and docs from it.
2. Separate authentication from authorization. A valid credential is evidence of a principal, not a permission verdict.
3. Resolve scope from canonical state. Do not trust client-selected departments or resource relationships.
4. Decide command authority in the state-change transaction. Recalculate the decision on retry.
5. Keep roles and permission bundles as typed grants. Do not turn them into wildcard decisions.
6. Preserve exact idempotent replay. A changed status or response body is not exact replay.
7. Use operation semantics, not route totals, for parity.
8. Keep missing evidence unknown. Absence of a witness is not equivalence.
9. Treat generated artifacts as projections. Correct drift at source.
10. Use explicit amendments to supersede frozen contracts.
11. Keep external effects separate from repository work.
12. Record limits beside every runtime claim.
